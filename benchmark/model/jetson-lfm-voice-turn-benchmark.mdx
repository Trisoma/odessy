# Odessy v0.1.0 Jetson LFM Voice-Turn Benchmark

Date: 2026-09-20
System under test: Jetson Orin Nano Super 4GB
Benchmark area: real voice-turn path with instrumented agent timing
Result directory: `benchmark/model/20260920-041633`
Status: successful benchmark completed

## Executive Summary

This benchmark evaluated the delay inside Odessy's real voice-turn path after
agent turn instrumentation was added.

The key result is:

```text
The slow agent gap is LFM proposal generation.
It is not MCP transfer.
It is not proposal parsing.
It is not repair generation.
It is not tool execution.
```

The successful run also confirmed that the repeated benchmark is stable when
Kokoro ONNX is forced to CPU. Earlier failures with ONNX Runtime auto mode
were caused by TensorRT/CUDA memory pressure, not by the LFM agent path.

## Addendum: Proposal-Path Re-run After Streaming (2026-09-23)

Date: 2026-09-23
Result directory: `benchmark/model/20260923-075345`
Scenario: `lfm_compare` (proposal-only; no STT, TTS, or playback)
Status: successful, 15/15 rows `ok`

This re-run followed the replacement of the whole-request 120 s HTTP timeout
with a per-chunk idle timeout (`ODESSY_MODEL_PROGRESS_TIMEOUT`, default 120 s).
See `docs/optimization/tool-harness-design.md`.

### Command

```bash
python -m benchmark \
  --scenario lfm_compare --adapter real \
  --prompt "on my laptop, run pwd" --expected-tool laptop.terminal.run \
  --lfm-variant current=lfm2.5-thinking:1.2b-q8_0 \
  --lfm-variant minimal=lfm2.5-thinking:1.2b-q8_0@false \
  --lfm-variant low=lfm2.5-thinking:1.2b-q8_0@low \
  --runs 4 --warmup 1
```

### Results

```text
rows                    15 (3 warmup + 12 measured)
status                  ok for all 15
timeouts                0
total_ms                22640 - 30919 (variant medians 24.6 / 25.0 / 25.3 s)
throughput              ~17.6 tok/s

thinking_chars          current ~1601-1968 | minimal 0 | low ~1684-1962
```

### What this establishes

Tool selection is correct on the real model: every sample chose
`laptop.terminal.run`, every proposal validated on the first model call, and no
repair was triggered.

`think=false` zeroed `thinking_chars` while leaving token counts materially
unchanged, consistent with the earlier finding that it removes reasoning text but
not generation work.

The three variants are indistinguishable on this prompt (medians within 2%). The
earlier ranking, in which `think=low` was worst on tool prompts, does not appear
here.

No timeout occurred, so nothing in this run contradicts the streaming change.

### What this does NOT establish

**It does not validate that the 120 s failures are gone.** The earlier failing
run generated 1004-1824 tokens over 70-115 s. This run generates 392-536 tokens
over 22-31 s. The workload is roughly a third the size and never approached the
120 s boundary, so the absence of timeouts is not evidence that the boundary was
removed.

Demonstrating that would need a single generation pushed past 120 s that then
completes cleanly. Recording the distinction explicitly because "no timeouts"
reads like a fix and is not one.

## Architecture Context

The measured voice-turn path was:

```text
fixed input WAV
  -> Whisper.cpp STT
  -> Odessy agent turn
  -> LFM2.5 through Ollama-compatible API
  -> Kokoro ONNX TTS
  -> audio playback command
```

The agent runtime remains model-independent:

```text
model proposes
  -> Odessy parses and validates
  -> policy checks
  -> optional MCP tool execution
  -> final text
```

For this benchmark input, no tool was called.

## ONNX Runtime Diagnosis

Earlier repeated voice-turn attempts with ONNX provider auto mode produced
ONNX Runtime and TensorRT/CUDA errors:

```text
CUDA failure 2: out of memory
Falling back to ['CPUExecutionProvider']
Cannot find plugin: FastGelu
Cannot find plugin: SkipLayerNormalization
Cannot find plugin: DynamicQuantizeLSTM
Killed
```

The successful result in this report was collected after forcing:

```text
ODESSY_ONNX_PROVIDER=cpu
```

This strongly indicates that the instability was in the ONNX Runtime
auto/TensorRT/CUDA path under Jetson memory pressure. It was not a failure of
the LFM agent path.

## Current Engineering Conclusion

The current stable Jetson voice-turn configuration is:

```text
STT: Whisper.cpp CPU
Agent/model: LFM2.5 through Odessy LlamaCppLFMModel
TTS: Kokoro ONNX CPU
Pipeline: sequential voice turn
```

The main latency contributors are:

```text
1. LFM proposal generation: median about 12.93 s
2. Kokoro ONNX CPU synthesis: median about 6.81 s
3. Audio playback: median about 3.43 s
4. Whisper.cpp STT: median about 1.44 s
```

The highest-value optimization targets are therefore:

- reduce LFM prompt and response cost;
- keep the TTS engine warm across turns;
- continue evaluating PyTorch Kokoro CUDA as the low-latency TTS candidate;
- keep ONNX Runtime TensorRT/CUDA disabled for repeated voice-turn benchmarks
  until the memory and plugin issues are resolved.

## Practical Recommendation

For stable repeated benchmarks on the 4GB Jetson, use:

```bash
ODESSY_ONNX_PROVIDER=cpu python -m benchmark \
  --scenario voice_turn \
  --adapter real \
  --audio-path /home/jaimef/odessy/output.wav \
  --runs 3 \
  --warmup 1
```

For single live smoke tests, `python -m odessy voice` remains useful because it
executes one bounded turn and exits. The repeated benchmark is stricter: it
exposes runtime initialization, residency, and cleanup problems that a single
turn can hide.

## Controlled LFM Comparison

A proposal-only comparison was collected on 2026-09-20 in:

```text
benchmark/model/20260920-091050
```

This run intentionally measured only the LFM proposal path. It did not invoke
STT, TTS, playback, or MCP. The same prompt and Ollama runtime were used for
all configurations:

```text
prompt: How are you doing?
model: lfm2.5-thinking:1.2b-q8_0
measured runs per configuration: 3
warmup runs per configuration: 1
```

| Configuration | Model latency | Prompt eval | Generation eval | Generated tokens | Generation tok/s | Valid proposal |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| current/default | 11.936 s | 134 ms | 11.474 s | 179 | 16.10 | yes |
| `think=false` | 11.693 s | 130 ms | 11.228 s | 179 | 16.32 | yes |
| `think=low` | 11.396 s | 142 ms | 10.941 s | 176 | 16.21 | yes |

All configurations made one model call per proposal. Parsing was approximately
0.01-0.02 ms, so it is negligible compared with model generation. Prompt
processing was also small, around 0.13-0.14 s; generation accounted for about
10.94-11.47 s of the roughly 11.4-11.9 s model latency.

The controlled result therefore confirms:

```text
The LFM delay is primarily generation/evaluation throughput.
It is not prompt prefill.
It is not parsing.
It is not repair or MCP execution.
```

`think=low` was the fastest measured configuration, approximately 4.5% faster
than the current/default setting. `think=false` was approximately 2.0% faster.
The difference is useful but modest, not a real-time breakthrough.

Thinking visibility changed as expected:

```text
current/default: thinking exposed, about 745-771 characters
think=low:       thinking exposed, about 745 characters
think=false:     thinking not exposed
```

However, Ollama did not expose a separate thinking-token count. The generated
token counts remained nearly identical, so this run cannot prove how many
hidden reasoning tokens were produced or eliminated. With `think=false`, the
visible final response was much longer, about 821-847 characters versus about
57 characters for the thinking-enabled variants. Proposal validity remained
true for every measured run.

Tool-selection correctness was not evaluated because this prompt required no
tool and the benchmark was run without `--expected-tool`.

## Updated LFM Recommendation

The next optimization target remains the LFM generation path. The evidence
supports testing prompt/output limits and a smaller compatible model before
changing inference runtimes. `think=low` is the current best latency candidate
among the tested settings, but it should be evaluated on tool-request prompts
with an expected tool before being considered a production policy.
