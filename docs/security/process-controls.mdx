`terminal.run` is a high-risk Odessy capability.
The model may propose a terminal action, but only the Python Odessy runtime can authorize it.

## Execution Authority

| Aspect | Detail |
|---|---|
| Default | `terminal.run` requires schema validation, policy classification, workspace cwd authorization, and confirmation when required. |
| Authority | Python `OdessyPolicy` and `CommandBridge` own the process authority boundary. |
| Protocol | MCP carries only an already approved request. |
| Execution server | The local MCP server invokes the command bridge; it does not decide model authority. |
| Recommendation | Keep terminal policy and confirmation outside the model and outside MCP. |

## Process Confinement

Authorization decides whether a command may run. Confinement decides what it can reach
once it does. v0.2.0 had authorization only; **v0.3.0 adds confinement**, and every
executor now routes its argv through `confine()`.

The backend is chosen by **what the host can actually enforce**, not by platform name:

```text
bwrap         Linux
landlock      Linux, via a launcher; unavailable where the kernel lacks Landlock
seatbelt      macOS
windows-acl   Windows, reporting `partial` by construction
unconfined    any -- the named, reported absence of confinement, not a backend
```

Each run reports the enforcement it achieved, so an unconfined run is *stated* rather
than inferred, and a run that requires isolation can never be satisfied by a backend
providing none.

This does not make `terminal.run` sandboxed on every host: on this board most backends
report unavailable. Per-host coverage is in `docs/reference/current-limitations.mdx`;
the design rationale is in the internal record
`../docs/execution-layer-design.md`.

## Working Directory

Every terminal request has an explicit working directory.
The cwd must resolve inside the configured Odessy workspace.

Denied examples include:

```text
run --cwd .. pwd
run --cwd C:\Users\...\outside pwd
run --cwd workspace-link-to-outside pwd
```

## Subprocess Environment

Odessy does not blindly inherit the parent environment.
The command bridge builds a small allowlisted environment needed for local command execution.

Commonly allowed variables include:

- `PATH`
- `PATHEXT`
- `SystemRoot`
- `COMSPEC`
- `TEMP`
- `TMP`
- `WINDIR`
- locale or terminal variables when needed

Obvious credential-shaped variables are excluded, including API keys, tokens, cloud credentials, provider keys, passwords, and private authentication material.

The tradeoff is intentional: some commands may need additional non-secret variables later, but adding them should be a deliberate runtime decision, not accidental inheritance.

## Timeout And Lifecycle

Every terminal request has a bounded timeout.
On timeout, Odessy returns a structured timeout observation and attempts request-scoped cleanup.

On Windows, cleanup uses the platform process tree tool.
On POSIX platforms, cleanup uses the process group where practical.

This is not a universal process jail.
It is a v0.3.0 local single-user lifecycle boundary.

## Background And Detached Execution

Odessy v0.3.0 is request-scoped.
Intentional background or detached execution is outside the authority model.

The policy layer denies obvious detachment patterns such as:

- `nohup`
- `disown`
- `setsid`
- `Start-Process`
- `Start-Job`
- `cmd /c start`
- shell background suffixes such as `&`
- detached flags such as `--detach`

Odessy does not claim to parse every shell language perfectly.
Policy detection is paired with execution-level timeout and cleanup controls.

## Output Bounds

Terminal stdout and stderr are bounded.
Output at or under the inline budget is returned unchanged.
Larger output keeps both a head and a tail window, so build and test failures at the end of a long run stay visible, and the result carries a structured truncation flag, an exact omitted-byte count, and a locator.

The full text is written to `.odessy/spill/` inside the workspace before the inline preview replaces it, so nothing is silently discarded.
If that write fails, the untruncated original is returned rather than a lossy cut.

This prevents a model-requested command from flooding logs, observations, or model context without destroying the output it bounded.

Output is also redacted for credential-shaped values before it is exposed or spilled.
That redaction is name-based and covers **both** terminal executors -- this
`terminal.run` path and the Node command path (`terminal.run` in single mode,
`laptop.terminal.run` in split mode), the latter since v0.3.0. Since v0.4.0
development it also covers every MCP tool result at the observation boundary, and the
Node file, search and Git tools at their own boundary.
See `docs/security/credential-handling.mdx`.

## Current Limitations

In paired split deployments, mutual TLS authenticates enrolled hosts; it does not
approve commands or replace confinement. The coordinator rechecks its local trust
state before dispatch, and the execution host independently enforces its enrolled
peer's capability and workspace grant. Revocation stops admission and initiates
cleanup; completed effects are not undone. See [host pairing](../reference/host-pairing.mdx).

Odessy process control is a local v0.3.0 authority boundary plus best-effort confinement,
not a complete OS sandbox. Coverage depends on the host, and on this board most backends
report unavailable.
Timeout cleanup is best effort, shell command parsing is intentionally limited, and intentionally detached descendants may require stronger OS primitives in a future version.

For the full current limitation register, see `docs/reference/current-limitations.mdx`.
