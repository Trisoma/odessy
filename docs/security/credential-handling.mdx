Odessy handles model credentials by **reference, not by value** in ordinary configuration.

## v0.5.0 development: cloud model credential storage

Settings → Models and connections can save a masked API key through the local
stdio helper into Windows Credential Manager or Linux Secret Service. Only those
native `keyring` backends are accepted; plaintext/file and chained backends are
rejected. When the OS service is unavailable or locked, explicitly choose **Use
for this session only**. No credential is written to the model configuration.

For each provider/origin/reference scope, resolution is environment → session →
OS store → missing. Explicit environment references do not fall back to another
provider key. Environment-supplied values are read-only in Settings. Status exposes
only configured/source/writable/persistence metadata; there is no secret-read API.
Managed credentials are resolved on each provider request. Session updates use a
revisioned private stdin channel and require coordinator acknowledgement.

The Node tool server no longer inherits ambient provider keys or the coordinator
token. Existing terminal and external-process allowlists remain in place. This
prevents routine disclosure, **not arbitrary code running with your user account**
from accessing that account's environment, memory or native credential service.

`odessy[ui]` includes `keyring>=25.0,<26`. Rebuilt desktop bundles must carry the
resolved UI dependency wheels and notices. Historical pinned installer dependency
sets are not silently rewritten or upgraded. See [implementation and verification](../setup/secure-model-credentials.md).

The remaining sections record the earlier policy and general-purpose tool-credential
limitations. Their historical "no store" statements do not describe the new cloud
model credential store, which is not a general credential-injection API for tools.

A credential is something the runtime resolves at the execution boundary.
It is never something the model holds, echoes, or reasons about directly.

## The Policy

### 1. The model requests credentials by reference only

The model may ask for a credential **by name**.
It may never receive, produce, or reproduce a credential value.

This mirrors the authority rule that already governs `terminal.run`: the model can propose an action, but only the Python runtime can authorize it.
A credential reference is a *name*, not an authorization.

### 2. Model-generated configuration may contain references, never values

Anything the model writes — a tool argument, a proposed config value, a generated script — may contain a credential **reference**.
It must never contain a credential **value**.

Where a value is genuinely needed, the runtime supplies it at the point of use.

### 3. Python Odessy stays authoritative

The Python runtime validates every request before resolution happens.
A credential reference does not skip, reorder, or weaken any existing gate.

Resolution is attempted **only after** the normal policy checks have passed: schema validation, policy classification, and confirmation where required.

### 4. Resolution happens at the execution boundary

A reference is resolved as late as possible, at the moment the action executes — not when the request is parsed, and not when a plan is formed.

Resolving early would place the value in intermediate structures, and every intermediate structure is a potential leak surface.

### 5. The resolved secret never becomes model-visible or persistent

Once resolved, a credential value must not appear in:

- observation content returned to the model;
- spill content written to disk;
- debug logs;
- error bodies or exception messages.

This is the same boundary the output-redaction work enforces for tool output. See [Output Spill And Redaction](#related-controls).

### 6. Introspection exposes metadata only

`describe()`-style introspection may report:

- **set** or **unset**
- which name is configured
- which provider or source a reference points at

It must never report the value itself.
The principle is the one the tool-call contract already follows: *a name is safe to print, a value is not.*

### 7. A reference grants no authority

Naming a credential does not authorize using it.
Policy classification and confirmation requirements apply exactly as they would to any other request.

A reference is a *pointer*, never a *permission*.

### 8. Cloud provider API keys are runtime-side, never model-side

The optional cloud model backends read their provider key from the environment
(`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `DEEPSEEK_API_KEY`, `DASHSCOPE_API_KEY`,
`MOONSHOT_API_KEY`, or `ODESSY_CLOUD_API_KEY`) inside the runtime, and send it only to
that provider. The key is never placed in a prompt, a tool argument, or an observation,
and `config/odessy.env` must not contain it.

Two limits follow, and neither is a guarantee:

- The key lives in the process environment for the lifetime of the run, so anything able
to read that process's environment can read it.
- Selecting a cloud backend sends the user's text and tool observations to the provider.
That is a **data-egress** boundary rather than a credential boundary, but it is why the
key exists. See `docs/reference/cloud-models.mdx`.

OpenAI-compatible assistant responses can also contain `reasoning_content`.
Odessy retains this provider-generated field unchanged in conversation history
and sends it back on tool follow-ups and repair retries, as DeepSeek requires.
It is not passed through the user/tool-result redaction filter. This preserves
the provider's conversation state; it does not add credential-reference
enforcement or broaden the filter's documented guarantees.

## What Is Not Yet Enforced

This section exists because the policy above is **not** implemented as a resolver, vault, or credential store.

```text
Not implemented:
  no credential store, vault, or resolver service
  no runtime substitution of a reference into a resolved value
  no config schema that marks a field as a credential reference
  no describe() surface for credentials

Therefore:
  the policy above is a design contract, not an enforced guarantee
```

What **is** implemented today is narrower and should not be confused with the policy: name-based **redaction** of credential-shaped values on specific surfaces.
Redaction is best-effort text filtering; the reference policy is a structural rule about where values are allowed to exist at all.
They are not equivalent, and redaction is not a substitute for the reference policy.

### Redaction currently covers

| Surface | Covered |
|---|---|
| `terminal.run` stdout/stderr (Python executor), before retention and before spill | Yes |
| Node executor stdout/stderr (`terminal.run` in single mode, `laptop.terminal.run` in split mode), before retention and before spill | Yes, since v0.3.0 |
| Every MCP tool result — built-in tools and configured third-party servers — at the observation boundary, before it is logged or sent to the model | Yes, since v0.4.0 development; a field whose name says it is a credential is redacted whatever its value looks like |
| Node tool results: `filesystem.read` content, `filesystem.list`, `project.find`, `project.grep` matches, and the Git text tools | Yes, since v0.4.0 development; file content and Git text also go through retention and spill |
| Model-adapter HTTP error bodies | Yes |
| Debug model-repair and parse logs | Yes |

### Redaction currently does not cover

| Surface | Covered | Why it matters |
|---|---|---|
| Detection accuracy | Name-based only | A secret under an innocuous name, or in an unrecognised shape, is not caught. |
| Values that never pass through a tool result | No | A credential written directly to a file by a tool's own side effects (outside its returned result), or sent by a third-party server's own network activity, is outside this boundary. |

The Node executor's coverage arrived in v0.3.0 and tool-result coverage in v0.4.0
development. Before that, redaction covered **executor output**, not **tool results in
general**; an observation from `filesystem.read`, `project.grep` or a Git tool was not
filtered. It is now filtered at one boundary in the Python runtime, and at the tool
boundary in the Node server, so a tool added later cannot silently return a secret.
Both boundaries also treat a credential-bearing **field name** as evidence: an opaque
`{"password": "correct-horse-battery-staple"}` matches no token shape and no
`NAME=value` pattern, but the name is enough to replace the value.

Redaction is also not a control that authorises handling real credentials.
