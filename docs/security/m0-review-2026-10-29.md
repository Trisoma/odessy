# M0 technical review — October 29, 2026

Decision: **NOT APPROVED / production implementation blocked by the existing M0
prerequisite**. This report is a technical review, not a third-party cryptographic
audit or a certificate of security. No production enrollment was enabled.

## Findings verified against repository and upstream source

1. **The candidate is not a complete protocol.** The profile table selects SPAKE2,
   HKDF, HMAC, AEAD and a TLS exporter without normative transcript encodings,
   complete message ordering, exact labels or transport bootstrap. Implementing it
   would still mean designing a new composition, prohibited by the agreed plan.
2. **RFC 9382 compatibility is unestablished.** `spake2 0.4.0` implements an
   Ed25519-group protocol whose source derives a 32-byte result using its own
   password/identity/message hashing. A primitive named SPAKE2 does not imply
   byte compatibility with RFC 9382's complete transcript/KDF/confirmation suites.
3. **The proposed initial TLS channel is unspecified.** Existing mTLS correctly
   trusts only enrolled peers; it cannot bootstrap two unknown peers unchanged.
   The pairing channel must have an independently justified bootstrap and binding.
   Do not add an arbitrary-certificate verifier to the existing execution channel.
4. **AEAD records are not defined.** ChaCha20-Poly1305 needs a complete 96-bit nonce
   definition and associated data, exact directional derivation, record order,
   exhaustion and error handling. The current “64-bit sequence prefix” is incomplete.
5. **The only exchange implementation is an insecure test adapter.** Its public
   code hash permits offline guessing and its confirmation is not a keyed MAC.
   Its passing tests are lifecycle evidence, not production authentication evidence.
6. **Certificate possession parsing must not be promoted unchanged.**
   `profile.rs::certificate_public_key` searches certificate bytes for an algorithm
   prefix instead of structurally parsing the certificate's actual SPKI. This is
   not sufficient evidence that the proof key is the leaf certificate's key. Use a
   reviewed certificate parser or an established transport's possession checks.

## Required evidence before approval

- Exact complete upstream construction and pinned implementation (or a fully
  specified profile reviewed by a qualified protocol reviewer), supported platform
  and Rust version, dependency provenance and license/audit status.
- Normative bytes/messages, roles, transcript, channel bootstrap, identity binding,
  mutual confirmation, protected records and all terminal failure behavior.
- Published vectors for that exact implementation/suite, plus an independently
  implemented endpoint reproducing full transcript and protected-message results.
  Two sides using the same Rust functions are not interoperability evidence.
- Independent assessment of the complete construction and Odessy's adaptation.
  A separate AI code review can find defects; it does not establish this approval.

No new custom protocol, dependencies, listener or cryptographic implementation was
added in this review. Existing Rust mTLS and the production fail-closed gate remain
unchanged. Ordinary user approval cannot substitute for missing authentication.

## Review outcome and verification

A separate fresh-context reviewer independently reached **not approved**, confirming
the unresolved protocol/transport bootstrap, public-hash confirmation, certificate
SPKI extraction and RFC compatibility findings. This was a separate AI technical
review, not independent professional cryptographic approval. The author did not
overrule it or substitute an approval flag.

`cargo test --locked --bin odessy-link pairing_boundary_tests --quiet`:
**5 passed**, 109 filtered out. These tests establish that the production boundary
remains closed and that existing trust reload/revocation checks retain their tested
behavior; they are not production cryptographic or interoperability vectors.

The requested approved production protocol and its vectors were **not delivered**.
The concrete blocker is the absent complete approved construction, not device
availability, UI work or an arbitrary demand for additional testing. Under the
existing pre-code M0 requirement, writing our own remaining cryptographic recipe
would violate the requested boundary. No production code was changed in this review.
