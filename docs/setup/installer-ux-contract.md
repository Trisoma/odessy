# Installer UX backend contract - October 24

Shared handoff for Codex (Python/native packaging) and DeepSeek (Flutter). Existing
JSON-line `odessy.setup.bridge` request/reply envelopes remain compatible. Views
call typed controllers; native adapter owns processes, file pickers and shutdown.

## Existing operations retained

Use `operation: "manage"`, `parameters.action` for context, package-review,
package-install, package-status, package-launch, installed-spec and packaged
maintenance operations. Keep selection/root/payload/confirm validation unchanged.
Review returns plan_id; mutation must submit that exact token. No automatic retry.
`cancel_file` remains the cooperative cancellation mechanism.

## Additive status and embedded output

`package-status` accepts optional `log_cursor` (nonnegative integer, default 0).
Existing fields remain: operation, status, stage, steps_done, steps_total, active,
registration and service_recorded. Add:

- `elapsed_ms`: nonnegative operation elapsed time, null when unavailable.
- `stage_elapsed_ms`: nonnegative active-stage elapsed time, null when unavailable.
- `logs`: ordered entries `{seq, timestamp, stage, stream, line}`; stream is
  stage/stdout/stderr. Lines are redacted before persistence or transmission.
- `log_cursor`: latest available sequence; `logs_truncated`: requested history fell
  outside the bounded buffer. Retain at most 2,000 lines / 256 KiB; no secrets/raw
  environment dumps. Export only the redacted representation after user action.

Poll through a separate read-only helper during mutations. Do not make the view
rehash the payload or manufacture percentages. Existing stage/file totals may be
used only within that stage. Missing totals mean indeterminate progress.

## Launch, uninstall and window handoff

Windows bootstrap invokes `--setup`; payload arrives through ODESSY_SETUP_PAYLOAD.
Keep --payload and --install-root compatibility. Add `--uninstall --install-root
<root> --payload <helper>`: open the uninstall review only, never apply it.
Installed apps UninstallString uses --uninstall; ModifyPath uses --manage.

For explicit setup-to-app handoff, package-launch accepts optional `launch_id`
(32 lowercase hex, generated by the trusted Dart adapter). It passes --launch-id
to the launched app and returns launched/pid/launch_id. Existing calls without it
remain compatible. Launched is not ready.

New `package-launch-ack` takes root, launch_id and state (`ready`,
`configuration_required`, `failed`). The installed app sends it only after its
window is rendered and startup has resolved. Do not include credentials or raw
failure text. New `package-launch-status` takes root/launch_id and returns state
(`pending` or the acknowledged state). Receipts bind to the launched active version
and are not approval grants. Unknown/obsolete identifiers fail explicitly.
Setup closes only for ready/configuration_required acknowledgement; failure or
timeout keeps setup visible. If implementing handoff later, leave setup open rather
than pretending Popen established readiness.

## Ownership and parallel-work boundaries

DeepSeek owns all Dart/pubspec changes and native-picker adapter. Codex owns Python,
packaging and native runner icon resources. Do not modify original UI plans.
Keep hashes, locks, exact confirmation and conservative retained-helper semantics.
No downloaded EXE deletion, shell self-deletion or visible helper consoles.

This is the agreed implementation interface, not a claim that all additions have
already landed. Any necessary amendment must be communicated before changing it.

## Already-open desktop handoff

Additive manage action package-launch-pending accepts root and optional version, returning up to 64 current-installation/current-version pending launch_ids. A rendered desktop polls on a separate helper, acknowledges at most eight per pass, and cancels polling on disposal. It never equates process creation with readiness. Existing setup closes on ready/configuration_required and stays open on failure.

## Launch helper stream isolation

The launched desktop receives DEVNULL for stdin/stdout/stderr and close_fds=True. It must not inherit bridge response pipes: clients drain stdout/stderr before reading the launch result, so inherited pipes prevent setup from reaching its existing close-on-readiness path while the desktop is alive. An acknowledged receipt alone does not prove the launching helper finished.
