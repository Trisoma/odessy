Host pairing is **optional** and included in released v0.4.0 via PR #27
(`47b2d8d`). Windows loopback and Windows–Jetson LAN discovery/mTLS/tool smoke
checks passed; see the qualification note at the end for remaining limits.
Planned v0.5.0 Go health aggregation/device inventory must reuse authenticated
host identity and admission; it does not replace pairing, grants or execution policy.
It replaces the raw remote MCP URL of
`split` deployments with a mutually authenticated connection to `odessy-link`, and
keeps the existing division of authority:

**Python coordinator → owned stdio → Rust client → mutual TLS → Rust host → owned Node stdio server**

- **Python** keeps action decisions, confirmations, sandbox escalation and approval
  audit.
- **`odessy-link`** admits only enrolled peers, binds the granted capability and
  workspace, owns the child process, and enforces the relay limits.
- **Node** keeps argument validation, workspace restrictions and confinement.

Nothing here claims identity *authentication of a person*; it authenticates two
machines that were enrolled by their operators.

## Enrolment

Each machine generates an ECDSA P-256 installation CA and a CA-signed connection
certificate valid for one year (the CA for five). The certificate carries both client
and server authentication usages and a DNS name `p-<installation-id>.odessy.invalid`.

```powershell
odessy-link init
odessy-link identity export --out peer.json
```

Both operators exchange bundles and compare the **full SHA-256 fingerprint** through
an independently trusted channel:

```powershell
odessy-link pair add --alias jetson --certificate jetson.json --expect-sha256 <fingerprint> --address 192.0.2.10:7443
```

Enrolment grants no execution access. The host operator must also grant it:

```powershell
odessy-link peers grant jetson --capability mcp --workspace D:\work
odessy-link peers list
odessy-link peers revoke jetson
```

Re-enrolling an alias replaces the certificate **and drops its grants**.

## Connection rules

- The client trusts only the selected peer's enrolled CA, and verifies the expected
  SAN from that record — not the connection address and not any advertised name.
- Client certificates are mandatory; the server identifies the peer by the exact
  fingerprint of the presented certificate, so a valid chain with a substituted leaf
  is refused.
- Both ends require that exact match **before any MCP byte is forwarded**.
- Session resumption is disabled. No accept-any verifier exists in the codebase.
- Handshake timeout is 10 seconds; operation deadlines remain the caller's.

Relay limits: 8 MiB per frame, 16 MiB buffered per direction, 32 outstanding requests
awaiting a response per direction, duplicate request ids rejected (numeric `1` and
string `"1"` are different), notifications do not consume request slots, and a
disconnect leaves unresolved work **unknown** — never replayed, never described as
exactly-once.

A response releases the requesting direction's slot, whichever stream carried it, and both
streams are linked in both roles: a request the Node server itself starts is answered on
the peer-to-node stream, and its slot is released there. Each direction therefore keeps
its own 32-slot budget, its own id namespace and its own journal rows, so numeric and
string ids never collide across directions and a long session is not capped at 32
requests overall. A request refused for the cap is never forwarded and leaves no journal
row: the session reports the refusal, not a phantom request. The content-free journal records
peer/session identity, request id, state and timestamps (no payloads, no credentials).
It never evicts a used id while a session is live and never evicts unresolved work, so
its size is bounded by refusing further ids rather than by forgetting them: a session
may use `ODESSY_LINK_MAX_SESSION_ITEMS` ids (default 4096) and then needs a fresh
session. Only fully settled sessions are pruned, keeping the 200 most recent.

Revocation is enforced three ways: admission is refused once the grant is gone, every
request re-checks the local registry and the granted workspace, and a one-second watcher
terminates a **live** session whose grant disappears. When a session ends or is revoked,
the host sends TLS `close_notify` first, so the peer sees an end of session rather than
an unexplained transport failure, and the peer stops waiting for answers that will not
come.

Process ownership: the host spawns the Node server with a minimal environment allowlist
and terminates the whole process **tree** (not just the direct child) when the session
ends, with a bounded wait for the child to answer first. Anything it could not confirm
is reported instead of being described as clean.

## Configuring Odessy

```powershell
$env:ODESSY_PAIRED_HOST = "jetson"
$env:ODESSY_LINK_BIN = "D:\odessy\native\odessy-link\target\release\odessy-link.exe"  # optional
```

`ODESSY_PAIRED_HOST` selects split execution. These combinations are rejected before
any connection is attempted, and a paired host never falls back to a legacy URL:

- `ODESSY_PAIRED_HOST` together with `ODESSY_DEPLOYMENT=single`;
- `ODESSY_PAIRED_HOST` together with `ODESSY_MCP_SERVER_URLS` or
  `ODESSY_TOOL_SERVER_URL`;
- `ODESSY_LINK_BIN` without `ODESSY_PAIRED_HOST`.

Tools from the peer keep the names the peer's own server uses — the served Node
server registers `laptop.terminal.run`, so Python sees exactly that and applies the
existing policy and tool contracts. The enrolled alias stays in execution-target
metadata, and with it the enrolled certificate fingerprint and the local grant
revision taken from `odessy-link peers list --json`, so an approval names the
certificate that will be trusted rather than a bare string.

## Discovery

### Directional execution consent

The coordinator now requires a separate explicit **Use for tools** review in
Devices, bound to the enrolled certificate and the current local trust revision.
Existing inbound `mcp` grants are not converted into outbound permission. After
updating, existing paired users must review their execution target and reconnect;
chat remains available while consent or the executor is unavailable. Disabling
the selected target does not silently select local execution.

The receiving host still independently enforces its incoming workspace grant.
Changing enrollment, revocation, consent or relevant revisions invalidates pending
dispatch authorization. Trust roots are reloaded for each new TLS connection.

## Short-code pairing

Production short-code enrollment is **closed**: no complete, reviewed protocol
profile exists, so `odessy-link pairing capabilities` answers
`supported: false, reason: protocol_review_required`, `pairing begin` creates no
session and opens no listener, and no code is shown. The decision, the candidate
construction, the threat model and the exact blockers are in
[the M0 profile record](../security/m0-pairing-profile.mdx).

Everything around that decision is implemented:

```powershell
odessy-link pairing capabilities            # what this build can do
odessy-link pairing status                  # newest session, truthfully
odessy-link pairing begin --workspace D:\work
odessy-link pairing listen --listen 0.0.0.0:0 --advertise --seconds 120
odessy-link pairing join --address 192.0.2.10:41415 --code-stdin   # code on stdin
odessy-link pairing confirm --session-id <id> --review-token <token> --workspace D:\work
odessy-link pairing cancel
```

- A code is exactly six digits, leading zeros included (`042137`), valid for 120
  seconds.
- Three authentication attempts are allowed per window and are reserved **before**
  the code is compared, so concurrent guesses cannot share the last attempt. Two
  unauthenticated connections may be open at once, released when an exchange ends.
- Frames are capped at 64 KiB, each direction at 256 KiB, and every message has a
  five-second deadline.
- An authenticated request is `awaiting_approval` and **is not trust**. The local
  operator's approval commits the identity first and the reviewed workspace second,
  in durable stages with a durable operation id. Re-running the approval is the same
  operation: it does not grant twice.
- A process that dies mid-commit leaves `incomplete` with reason `commit_interrupted`.
  Recovery never completes or reverts authority on the operator's behalf, and
  cancelling during a commit reports an unknown outcome instead of a rollback.
- A re-enrolled alias with a different certificate needs an explicit replacement; it
  never silently inherits the old peer's access.

The enrollment exchange itself exists only in a **test adapter**, built with
`--features test-profile` and run with `ODESSY_LINK_TEST_PAIRING_ADAPTER=1`. It proves
the mechanisms above (transcript binding, mutual ECDSA possession proofs, mutual key
confirmation, limits, staging, recovery) but it is not a PAKE, so it offers no offline
guess resistance and must never be described as approved enrollment. A release build
contains no such code path.

## Executor companion

`odessy-executor` is the packaged Windows executor's whole user interface: one window
that shows the shared folder, opens a pairing window, displays the code and the
status, approves an authenticated request, and can be sent to the background instead
of blocking the desktop.

- It resolves `odessy-link.exe` from **its own verified package directory**, never
  from `PATH`, and verifies `checksums.txt` before it starts (a development build
  without a manifest says so in the window instead).
- One instance only: a second launch focuses the running window.
- The pairing listener is a child of the window and stops with it; the close button
  asks whether to keep serving in the background or stop.
- Firewall, port and missing-component problems are reported in the window with an
  instruction. The companion never asks for elevation and never suggests disabling a
  firewall or another security control.
- `odessy-executor --selftest` verifies the package and asks the component for its
  capabilities, so packaging can fail before a user sees a broken package.

```powershell
pwsh -File native/odessy-link/package-executor.ps1 `
    -NodeDirectory C:\odessy\node -NodeServer C:\odessy\tool-server\index.js `
    -OutputDirectory build\executor-package
```

The script builds both binaries, assembles the Node runtime, tool server, notices and
icon, writes `checksums.txt`, and then runs the packaged `--selftest`. A missing
component is an error, not a warning.

Manual administrator enrollment (identity export, fingerprint comparison, `pair add`,
`peers grant`) remains available under **Advanced** in the desktop and is unchanged.

mDNS is an **address aid only**. It never enrols a peer, never grants a capability and
never replaces the enrolled identity:

```powershell
odessy-link discover --seconds 3        # what is advertised on this network
odessy-link serve --listen 0.0.0.0:7443 --advertise
odessy-link connect --peer jetson --discover
```

`--discover` fills in an address **only** when the peer has none recorded; an
advertisement whose fingerprint differs from the enrolled one is ignored, and among
several advertisements the enrolled fingerprint wins. TLS still proves the peer, so a
spoofed advertisement cannot redirect the session. If discovery is unavailable or finds
nothing, the explicit `--address` path is unchanged. Reconnecting after a certificate
change means re-enrolling: the running `serve` keeps using the admission records it
reads per connection, and a peer whose grant or certificate changed is refused on its
next connection.

Discovered addresses are formatted as socket addresses: IPv4 as `192.0.2.10:7443`,
IPv6 bracketed as `[2001:db8::10]:7443`. A link-local address (`fe80::/10`) is only
reachable through one interface and discovery carries no scope, so such a candidate is
reported as unusable instead of being handed to a connector that could never reach it;
a scoped form (`fe80::1%7`) is kept and its scope survives parsing.

## Diagnosing

```powershell
odessy-link peers list --json   # enrolment, grants, revision; no keys printed
odessy-link connect --peer jetson   # run before starting Odessy
python -m odessy doctor
```

`doctor` reports the configured alias, the binary it found, how many peers are
enrolled, the grant revision, and whether the alias is enrolled and holds `mcp`. It
reads the local registry only and prints no key material.

## Qualification and limits

Identity material is protected by the platform: Windows stores it through DPAPI
(user-bound ciphertext) and enforces an owner-only DACL. The owner is identified by the
current process token's **SID**, not by a user name, and the ACL is reset before being
narrowed, so an explicit grant that already existed (`Everyone: FullControl`, for
example) is removed along with inherited access. The resulting DACL is read back and the
call fails if anything but that SID still has access. Existing state is tightened when
it is read as well as when it is written, so a directory or identity file created by an
older build does not stay open. Unix creates the directory `0700` and files `0600` from
the first write. SQLite registry and journal files get the same owner-only treatment.
An existing plaintext Windows identity is migrated on first use, verified by a round
trip, and the plaintext copy is removed; `odessy-link` reports that it happened.

October 23 Windows–Jetson LAN tests passed discovery without a saved address,
enrolled-certificate mTLS, real Node listing/proof-file read, workspace rejection
and live revocation. Bare discovery switches were fixed and retested. Native ARM64
build/tests passed; Linux/ARM64 packaging remains unqualified. A Windows cleanup
warning occurred when `taskkill` could not find an already-ended Node PID;
inspection found no leftover child/listener. See the
[qualification record](../qualification/2026-10-23-interactions-and-pairing.md).
Remote coding-agent
hosting, MCU pairing, internet traversal and fleet management are out of scope.

Automated checks: `cargo test` and `cargo clippy --all-targets -- -D warnings` in
`native/odessy-link`; `tests/test_paired_host.py` and `tests/test_paired_agent.py` run
always; `tests/test_paired_transport.py` and `tests/test_paired_integration.py` run with
`ODESSY_LINK_E2E=1` and a built crate (the `pairing` CI job).

## Recovering from a conversation startup failure

A saved peer marked **Revoked** remains visible as a trust record; it is not a
corrupt database. Do not delete identity keys or the trust database to hide it.
A revoked peer cannot be used as the execution target until explicit verified
enrollment/authorization succeeds. Discovery never reverses revocation. Text chat
can continue with the selected model in explicitly labelled chat-only mode.

The desktop now keeps an already-started management API alive if conversation
initialization fails. The error offers **Open Settings** and **Open Devices**;
no tool work is retried or redirected to another host. Unavailable paired execution
starts a chat-only session with all tools, hooks and delegated jobs detached.
Unrecoverable model/session failures return a safe HTTP 503. Correct the
model/host configuration or re-enroll through an exact reviewed operation, then
explicitly reconnect to restore execution. Saving configuration alone is not activation.

Deploy both the rebuilt desktop and matching Python source update, then close
and reopen the existing application/coordinator. Replacing only the Flutter
bundle cannot update an already-running Python process.
