Odessy can use a cloud model in place of the local LFM or Gemma model. This is
opt-in and off by default. A cloud model is a stronger **proposer**, not a stronger
authority: every tool call it proposes still passes tool-contract validation,
workspace authority, policy, and human confirmation in the local Python runtime.

## Providers

| Backend | Provider | Protocol | API key variable | Default model |
|---|---|---|---|---|
| `claude` | Anthropic | Anthropic Messages API (official `anthropic` SDK) | `ANTHROPIC_API_KEY` | `claude-opus-5-5` |
| `openai` | OpenAI | OpenAI Chat Completions | `OPENAI_API_KEY` | `gpt-5` |
| `deepseek` | DeepSeek | OpenAI-compatible | `DEEPSEEK_API_KEY` | `deepseek-chat` |
| `qwen` | Alibaba Cloud DashScope | OpenAI-compatible | `DASHSCOPE_API_KEY` | `qwen-plus` |
| `kimi` | Moonshot AI | OpenAI-compatible | `MOONSHOT_API_KEY` | `kimi-k2-turbo-preview` |
| `custom` | Any OpenAI-compatible endpoint | OpenAI-compatible | `ODESSY_CLOUD_API_KEY` | none, set `ODESSY_CLOUD_MODEL` |

Provider model catalogs change. If a default model is retired, set
`ODESSY_CLOUD_MODEL` instead of editing code.

## Setup

The Claude backend needs the optional SDK:

```bash
pip install -e .[cloud]
```

Export the provider's key in your shell. Do not put keys in `config/odessy.env`,
which is committed.

```bash
export DEEPSEEK_API_KEY=...
python -m odessy --model-backend deepseek "run pwd"
python -m odessy voice --model-backend claude
```

Or select the backend persistently with `ODESSY_MODEL_BACKEND=claude`.

## Settings

| Variable | Applies to | Meaning |
|---|---|---|
| `ODESSY_MODEL_BACKEND` | all | `claude`, `openai`, `deepseek`, `qwen`, `kimi`, or `custom` selects a cloud backend |
| `ODESSY_CLOUD_MODEL` | all | Overrides the provider's default model |
| `ODESSY_CLOUD_BASE_URL` | all | Overrides the endpoint; required for `custom`. Use `https://dashscope-intl.aliyuncs.com/compatible-mode/v1` for Qwen outside mainland China, `https://api.moonshot.ai/v1` for Kimi's international endpoint |
| `ODESSY_CLOUD_API_KEY` | all | Overrides the provider's own key variable |
| `ODESSY_CLOUD_TIMEOUT` | all | Seconds per request, default 120 |
| `ODESSY_CLOUD_MAX_TOKENS` | Claude | `max_tokens` per request, default 16000 |
| `ODESSY_CLOUD_EFFORT` | Claude, DeepSeek | Claude: `output_config.effort` (`low`, `medium`, `high`, `xhigh`, or `max`, subject to model support). DeepSeek: `reasoning_effort`; see the example below. Unset keeps the provider default. Other OpenAI-compatible backends do not receive this setting. |
| `ODESSY_CLOUD_FALLBACKS` | Claude | `on` (default) enables server-side refusal fallbacks on models that support them; `off` disables |
| `ODESSY_CLOUD_RETRIES` | all | Retries after a rate limit (429), server error (5xx, 529), timeout or dropped connection, default 2. Waits 1 s, 2 s, ... or the server's `Retry-After`, at most 20 s. `0` disables. A 4xx such as a bad request or a wrong key is never retried |
| `ODESSY_CLOUD_MAX_RESULT_CHARS` | all | Characters of one tool result sent to the provider, default 16000; longer results are cut with a note saying how much was omitted |
| `ODESSY_MAX_MODEL_CALLS` | all | Model calls per turn, counting corrections and follow-up steps. Default 8 for cloud backends, 4 for local ones |

### DeepSeek with low reasoning effort

For the official DeepSeek API's documented `deepseek-flash` model:

```bash
export DEEPSEEK_API_KEY=...        # keep the real key out of committed files
export ODESSY_CLOUD_MODEL=deepseek-flash
export ODESSY_CLOUD_EFFORT=low
python -m odessy --model-backend deepseek "what time is it?"
```

PowerShell equivalents:

```powershell
$env:DEEPSEEK_API_KEY="..."
$env:ODESSY_CLOUD_MODEL="deepseek-flash"
$env:ODESSY_CLOUD_EFFORT="low"
python -m odessy --model-backend deepseek "what time is it?"
```

The adapter sends `"reasoning_effort": "low"` on every DeepSeek request,
including tool follow-ups and repair retries. It does not set a separate
`thinking` toggle. DeepSeek's [thinking-mode documentation](https://api-docs.deepseek.com/guides/thinking_mode)
documents thinking enabled by default and effort levels `low`, `high`, and `max`.
Use `low`, not `light`; the adapter forwards the configured value without
validating provider-specific levels. An alternate endpoint or model may behave
differently. The built-in model default remains `deepseek-chat`, so set
`ODESSY_CLOUD_MODEL` explicitly for this example.

DeepSeek requires assistant `reasoning_content` to be sent back when tools are
present. The adapter preserves that field whenever it appears in an
OpenAI-compatible response, including empty values, through subsequent requests
within the same conversation. A new `propose()` call starts a fresh conversation.
Reasoning is conversation state, not the final text spoken to the user.

For a cloud evaluation, use the same variables with:

```bash
python -m evals run --backend deepseek --label deepseek-low
```

See [the evaluation guide](../../evals/README.md) for a one-case smoke check and
provenance handling. The eval metadata records the model name, but not effort or
the provider-resolved model version; retain non-secret configuration notes with
results when comparing runs.

## How it differs from the local backends

- **All available tools are offered, and no keyword rules apply.** The model chooses
  the tool and the machine from the system prompt, which says what runs where. (The
  local adapters still reject a "my laptop" request that uses the wrong command tool;
  a cloud model reads "my laptop is off, run it here" correctly where that rule would
  not.) Without the Node server, single mode offers only time, calculator, and
  terminal tools. See [deployment](deployment.mdx).
- **Native tool-result messages.** Tool results go back as `tool` / `tool_result`
  messages tied to the call id, so the model sees the whole turn. Returned
  `reasoning_content` is retained for OpenAI-compatible conversations.
- **Native tool batches in v0.4.0 development.** Cloud adapters preserve multiple
  calls from a completed assistant response. Execution defaults to sequential;
  `ODESSY_TOOL_CONCURRENCY` permits bounded overlap only for eligible built-in
  tools. Authorization, ordering barriers, and cancellation still apply to each
  call. Text-JSON fallbacks remain singular. See [tool concurrency](tool-concurrency.mdx).
- **One repair per step.** An invalid proposal (unknown tool, bad arguments,
  malformed JSON) is sent back as an error tool result once. A second invalid first
  proposal fails the turn; a second invalid follow-up ends it with a summary of the
  last result.
- **Failures are marked as failures.** A rejected call, or one that ran and failed (a
  wrong path), goes back as an error tool result (`is_error` for Claude), so the model
  can correct it.
- **Transient errors are retried** (see `ODESSY_CLOUD_RETRIES`); the Anthropic SDK
  receives the same retry count.
- **Tool names are encoded.** Neither API accepts dots in function names, so
  `laptop.terminal.run` is sent as `laptop__terminal__run` and decoded on return.

## Data that leaves the machine

With a cloud backend selected, each turn sends to the provider:

- the user's text (the speech transcript in voice mode);
- the tool list and the system prompt;
- every tool result in that turn, which can include file contents, command
  output, and Git diffs;
- previous assistant messages, including returned reasoning content, when
  continuing a tool conversation.

The user text and every tool result pass through `redact_text` first. That
redaction is name-based plus a few known token shapes; it is best effort and
misses unrecognized secrets (see `docs/security/credential-handling.mdx`). Do not
point a cloud backend at a workspace whose files you would not send to that
provider.

Odessy prints a notice on stderr at startup when a cloud backend is active.

## Cost and usage

Every cloud call in a run is recorded in one ledger (`odessy.models.usage`),
whichever adapter or router made it.

**Prompt caching.** The tool definitions and system prompt are the same on every
call, and they make up most of each request.

- **Claude:** Odessy marks them cacheable with `cache_control`, so later calls in a
  turn, and turns within the cache lifetime, read them from the cache.
- **OpenAI, DeepSeek, Qwen and Kimi:** these providers cache a repeated prefix on
  their own. Odessy keeps the prefix byte-stable, with no timestamps and a fixed
  tool order.
- **Turning it off:** set `ODESSY_CLOUD_PROMPT_CACHE=off`. This affects Claude's
  markers only.
- **Minimum size:** a prefix below the model's minimum cacheable length is not
  cached, and nothing fails.

**Usage.** Each turn that used the cloud prints one line on stderr:

```text
[odessy] cloud usage: this turn 6,060 in (3,000 cached), 14 out (2 call(s)); run 18,230 in (...)
```

`in` counts all input tokens. `cached` is the part of `in` that was served from
the provider's cache. Turn diagnostics and eval attempts record the same
`cached_prompt_tokens`. A wake-listening session prints a total for the run when it
ends.

**Estimated cost.** Odessy ships no prices: they change, and they differ by
provider, region and plan. To get an estimate, set prices per million tokens:

| Setting | Meaning |
|---|---|
| `ODESSY_CLOUD_PRICE_INPUT` | Uncached input. Required together with output |
| `ODESSY_CLOUD_PRICE_CACHED_INPUT` | Cached input. Defaults to the input price |
| `ODESSY_CLOUD_PRICE_OUTPUT` | Output |
| `ODESSY_CLOUD_PRICE_CURRENCY` | Label only. Defaults to `USD` |

The estimate is labelled `~` because it can differ from your bill, for example
through cache-write surcharges, reasoning tokens or discounts.

**Budget.** These settings cap one run (one `python -m odessy` invocation, or one
voice session):

| Setting | Meaning |
|---|---|
| `ODESSY_CLOUD_BUDGET_TOKENS` | All tokens, cached or not |
| `ODESSY_CLOUD_BUDGET_COST` | In the price currency. Needs prices |

- The budget is checked **before** each request. Once it is reached, no further
  request is sent: a text turn stops with the reason, and a voice turn reports it.
- A warning is printed once at 80%.
- A turn can end mid-task when the budget runs out. Tools that already ran in
  that turn have run.
- A malformed price or budget setting stops a cloud run at startup.
- `python -m odessy doctor` shows the settings in effect.

## Not covered yet

- No streaming: each request waits for the full reply.
- No automatic fallback to the local model when the network or provider fails;
  the turn fails with the provider's (redacted) error.
- Costs are estimates from prices you set; Odessy does not read your provider bill.
- The budget is per run; there is no daily or cross-run limit.
- The component-performance `benchmark/` harness has no cloud adapter yet.
  Agent-behaviour evaluations in `evals/` do support cloud backends.
- Tests run against recorded response shapes, not live provider APIs.
