Odessy can offer the tools of third-party MCP servers to the model, next to its own.
A server is used only if it is listed in your `servers.toml`; being reachable is not
being trusted.

**Status: implemented in v0.4.0**, merged via PR #11 on
October 19, 2026. This is an extra feature beyond the initial roadmap and is not
part of the released v0.3.0 baseline. See the [v0.4.0 roadmap](../releases/v0.4.0.md).

Listing a `stdio` server authorizes launching that program locally, including
during startup discovery, before any individual tool confirmation. Listing an
`http` server authorizes contacting that endpoint and sending it tool arguments
on calls. The `trust` setting governs tool-policy decisions; `untrusted` does not
sandbox the program. Odessy's own command isolation does not automatically apply
to third-party servers. Their descriptions, schemas, annotations, and results are
third-party content, including descriptions sent to the model.

## The servers file

Location: `~/.config/odessy/servers.toml` (outside the repository). Set
`ODESSY_SERVERS_FILE` to use another path. Without the file, nothing changes.

```toml
[servers.notes]                  # the name is also the tool-name prefix
transport = "stdio"
command = ["notes-mcp", "--root", "notes"]
env = ["NOTES_DIR"]              # environment passed to the command, beyond the base set
trust = "trusted"                # "untrusted" (the default) or "trusted"
workspace_paths = ["path"]       # arguments that hold paths; kept inside the workspace
timeout = 30                     # seconds per listing or call

[servers.notes.tools.search]
policy = "allow"                 # "allow" | "confirm" | "deny", by the server's own tool name

[servers.notes.tools.delete_note]
policy = "deny"

[servers.tracker]
transport = "http"
url = "http://127.0.0.1:9000/mcp"
```

| Key | Meaning |
|---|---|
| `transport` | `http` (needs `url`) or `stdio` (needs `command`) |
| `env` | stdio only: variable names passed to the command. It always gets a base set (`PATH`, `SYSTEMROOT`, `HOME`, `TEMP`, ...) and nothing else |
| `trust` | `untrusted` by default. See the decision order below |
| `tools.<name>.policy` | Per-tool override. The only way to relax a decision |
| `workspace_paths` | Argument names whose values must stay inside the workspace and not name credential files, checked even when a tool is allowed |
| `timeout` | Seconds for starting the server, listing its tools, and each call |

Server names are lowercase identifiers, without `__` and not ending in `_` (cloud
adapters encode `.` as `__`). The built-in families (`git`, `filesystem`,
`terminal`, `project`, `time`, `calculator`, `log`, `laptop`) and `odessy` are
reserved. A malformed file stops Odessy with the file, server and problem named.

## How tools are offered

At startup each configured server is asked for its tools once. Its tools are offered
as `<server>.<tool>` (`notes.search`), so they cannot shadow a built-in tool or each
other. A server that does not answer is reported on startup and left out; the others
and the built-in tools are unaffected.

- **Descriptions** are written by the server's author. They are shortened and
  labelled `[Third-party tool from the notes server]` in what the model sees.
- **Arguments** are checked against the server's own JSON Schema before execution.
  Policy preflight can run before schema validation; confirmation may therefore
  be requested for arguments that are subsequently rejected.
- **Left out, with a reason:** tool names that cannot travel through every model
  adapter (anything but letters, digits, `_`, `.`, `-`, or containing `__` or `_.`),
  schemas
  that are not objects, invalid, larger than 8000 characters or nested deeper than 8.
- **Limit:** at most 64 third-party tools for a cloud model and 16 for a local one,
  in config order.
- **Results** may be text only; they reach the model as `{"status": "ok", "content": ...}`
  and are redacted and capped like any tool result, whatever the backend. Redaction is
  best effort: see `docs/security/credential-handling.mdx`.

## How a call is decided

Evaluated in order; the first rule that applies decides.

| # | Rule | Decision | Audit `rule` |
|---|---|---|---|
| 1 | `policy = "deny"` for this tool | deny | `config_deny` |
| 2 | A `workspace_paths` argument leaves the workspace or names a credential file | deny | `workspace_path` |
| 3 | `policy = "allow"` / `"confirm"` for this tool | allow / confirm | `config_allow` / `config_confirm` |
| 4 | The server is not `trusted` | confirm | `untrusted_server` |
| 5 | Trusted server, tool annotated `read_only_hint` and not `destructive_hint` | allow | `trusted_read_only` |
| 6 | Anything else (trusted, but destructive, unannotated, or not read-only) | confirm | `default_confirm` |

What a server says about its own tools only ever makes a decision stricter, with one
exception: rule 5, which applies only to a server you marked `trusted`. Marking a
server trusted is therefore a statement that you believe its annotations.

Odessy's sandbox modes govern its own command tools; a third-party tool that is sent
`sandbox_permissions` or `justification` without declaring them is denied
(`sandbox_arguments`).

When asked, you can answer `a` to allow every call to that one tool until Odessy
exits (held in memory only). A tool rated high risk (annotated destructive) is never
offered this and needs a typed `yes` each time.

A server must be listed to execute at all: the composition root wraps each listed
server that answered in `ExecutionTarget`, and nothing found at runtime is added.

## Sessions

A stdio server is started once, on first use, and its session is kept for the run:
the startup listing, every turn's listing, and every call share it. It is closed when
Odessy exits. An http server gets a connection per listing and call.

- A server that has exited is started again on its next use.
- A call that fails or times out is **not retried**: the server may already have acted,
  and you confirmed one call. Its session is closed, so the next call starts the
  server again.

If a caller directly issues concurrent calls through one shared stdio session,
a timeout or failure that closes it can also fail sibling calls. The built-in
scheduler ordinarily treats external tools as exclusive; opt-in concurrency for
selected built-in reads does not make third-party tools parallel.

## Audit log

Every call is recorded in `~/.local/state/odessy/external-audit.jsonl`, one JSON object
per line. `ODESSY_AUDIT_FILE` sets another path; an empty value turns
the log off. If the directory cannot be created, Odessy stops and says so; a later
failed write is reported once and the run continues. Odessy's own tools appear with
`"server": "builtin"` and no `trust` or `transport`, and the file keeps its name from
when it held third-party calls only.

```json
{"time": "...", "event": "decision", "server": "notes", "trust": "untrusted", "transport": "stdio",
 "tool": "delete_note", "decision": "confirm", "rule": "untrusted_server", "risk": "medium",
 "confirmed": false, "arguments": {"title": "<sha256>"}}
{"time": "...", "event": "call", "server": "notes", "trust": "trusted", "transport": "stdio",
 "tool": "search", "outcome": "ok", "duration_ms": 41.2}
```

- `decision` comes first for every proposed call. `confirmed` is `true` or `false` when
  you were asked, `null` otherwise. A denied or declined call has only this record.
- `call` follows for an executed call: `outcome` is `ok`, `error` (the server answered
  with an error), `timeout`, or `failed` (with `error_type`).
- **Arguments are names and SHA-256 hashes, never values.** Equal hashes show repeated
  input. A short or guessable value can still be recovered by guessing, so keep the
  log private.
- `rule` names the decision rule above; the free-text reason is left out because it
  can quote a path.

## Doctor

`python -m odessy doctor` has a "Third-party servers" section when a servers file
exists. It fails on a malformed file, and warns, with the fix, when:

- a stdio command is not on `PATH`;
- a server does not answer;
- a tool will be left out;
- the tool limit for the selected backend is exceeded;
- the audit log is off.

This check actively contacts each listed HTTP server or launches its listed stdio
command to discover tools. It uses that server's configured `timeout`, per server;
several unavailable servers can therefore make `doctor` take longer than one
timeout. Running diagnostics is not a passive configuration inspection.
