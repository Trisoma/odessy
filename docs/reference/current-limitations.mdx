Development-only collaboration adds an authenticated loopback session API and coding jobs. It does not provide durable jobs, verified child-CLI confinement, mid-task model takeover, or hardware qualification. Coding-agent bills are outside the API budget. See [model collaboration](model-collaboration.mdx).

Risk-aware voice approval and mid-task clarification are **complete offline and
independently reviewed as of October 22, 2026** on `feat/voice-user-interaction`
through `3412025`; merged via PR #24 (`6d8b80b`), unreleased. Real microphone echo
behaviour, Jetson operation and packaged-device acceptance remain unqualified.
Spoken approval signals intent and does not authenticate identity. See
[voice integration](voice-integration.mdx).

Cloud resilience merged via PR #23 (`d05e1b8`): configured pre-tool failover,
sentence-level cloud wake speech and a content-free egress log. No live-provider
or new Jetson qualification is established. Failover cannot resume a turn after
tools ran; streaming compatibility and acoustic interruption remain hardware/provider
checks. See [cloud models](cloud-models.mdx).

Odessy v0.3.0 has a real local command-line authority boundary, and an isolation layer whose coverage depends on the host.
It was released privately as a prerelease on October 19, 2026. Future feature work is
tracked in the [v0.4.0 roadmap](../releases/v0.4.0.md); those items remain unavailable
or undecided as described there. Wake listening, automatic model selection,
confirmation UX, and batch follow-ups are merged into `develop` as unreleased
v0.4.0 work; software integration does not qualify the Jetson hardware path.
See [Jetson wake testing](../jetson-wake-testing.md) for setup and acceptance.
It is still not a complete operating-system sandbox, and on the Jetson board it is largely inactive — see **Isolation Layer** below.
This page records the limits future agents must keep visible when changing the runtime, tools, policy, MCP integration, or public documentation.

## Product Scope Limits

| Area | Current state | Limitation |
|---|---|---|
| Model | LFM2.5-Thinking is the default Ollama backend; Gemma remains an explicit fallback; an optional cloud backend (Claude, or any OpenAI-compatible API) can replace both | The October 18 agent-eval runs provide fixture-based measurements for LFM and DeepSeek, not full quality, latency, memory, or long-run reliability validation. The cloud backend is opt-in and off by default — see **Data egress** below. |
| Voice | Staged voice loop is integrated and has completed live Jetson turns | Automated tests still use fakes for hardware components, and physical audio quality depends on the configured device. |
| GUI automation | Out of scope | No mouse, keyboard injection, screen capture, browser automation, desktop automation, or robotics. |
| Multi-agent behavior | Out of scope | No delegation, background autonomy, scheduler, or multi-session agent orchestration. |
| Writes | Node provides `filesystem.write` and `log.append` | Writes remain subject to tool validation and authority checks; availability depends on the mounted server. This is not arbitrary filesystem access. |

## Security Boundary Limits

| Area | Current control | Limitation |
|---|---|---|
| Workspace confinement | Python `WorkspaceAuthority` plus Node path guard defense in depth, **and** an isolation layer that confines wherever a backend exists | Path validation is still user-space, so TOCTOU races remain possible between validation and access. Kernel isolation is a separate, additive control — see **Isolation Layer**. |
| Symlinks/reparse points | Canonical path resolution blocks existing symlink escapes where the platform resolver exposes them | This is not a claim of complete coverage for every Windows reparse-point or filesystem race edge case. |
| Sensitive paths | Obvious sensitive names and segments are denied | The classifier is intentionally conservative, not a perfect secret detector. It may miss unusual secret filenames and may deny some legitimate files. |
| Command parsing | Policy denies destructive, credential-seeking, and obvious detached/background patterns, download-and-run (`curl … \| sh`, `iwr … \| iex`, `bash <(curl …)`), and writes to operating-system locations (`C:\Windows`, `/etc`, `/usr`, …) | Odessy does not implement a full shell parser, so these are patterns: an obfuscated command can evade them, and an interpreter fed by a download is denied even when it only formats data. Execution-level timeout cleanup is a backstop, not a universal containment proof. |
| Low-risk allow rule | Run without confirmation, only as a single command: listing (`pwd`, `ls`, `dir`, `Get-ChildItem`/`gci`, `Get-Location`); locating programs (`which`, `where`, `Get-Command`); `echo` without variables; `--version`/`--help` of a named list of well-known programs; read-only git (`status`, `log`, `show`, `diff`, `branch` listing, without `--output`, `--ext-diff`, `--textconv` or `--no-index`); file readers (`cat`, `type`, `Get-Content`, `head`, `tail`, `wc`) only when every file named is inside the workspace and not a credential file | Before, only the first word was checked, so `ls && python evil.py` was "low risk"; any chaining (`;`, `&&`, `\|`, backticks, `$(`) now needs confirmation. Parentheses and braces also require confirmation because PowerShell can execute commands inside expressions. This remains conservative pattern matching, not a shell parser. As with `git status`, a repository's own git config can make an allowed git command run a program; allowed commands run in read-only mode. Commands listed in `commands.toml` for a workspace skip the question but keep `workspace-write` mode and every earlier rule; prefix matching means an entry such as `pytest` also approves its arguments (`pytest -p plugin`). |
| Failed tool calls | A tool call that runs and fails (a wrong path) is returned to the model as an observation it can correct | The next call is validated and authorized like any other, and the per-turn model-call limit (`ODESSY_MAX_MODEL_CALLS`: 8 for cloud backends, 4 for local ones) still bounds retries. Before, one wrong path ended the turn. |
| Third-party MCP servers | **Implemented in v0.4.0 development, unreleased.** Only servers listed in `servers.toml` execute; their tools are namespaced, schema-checked, budgeted, and sent through the normal policy and authorization path | Annotations are self-reported: marking a server `trusted` means believing them. Listing a stdio server launches that command; an HTTP entry trusts the configured endpoint. A stdio server keeps one session per run, and a failed call is not retried. The audit log records argument hashes, not values; a guessable value can be recovered from its hash. Third-party tools do not automatically inherit Odessy's own command sandbox. See `docs/reference/external-servers.mdx`. |
| Cross-OS paths | The workspace check treats a Windows drive or UNC path as outside the workspace, and a backslash as a separator, on any host | Before this, on the Linux Jetson `C:\Windows\System32\x` was a relative file name inside the workspace, so a write there (bound for the Windows laptop) was only confirmed. The laptop's own path guard still rejected it. |
| Timeout cleanup | Windows uses process-tree termination; POSIX uses process-group termination where practical | Cleanup is best effort. Intentionally detached descendants may evade request-scoped cleanup without stronger OS primitives. |
| Environment isolation | `terminal.run` receives a sanitized allowlisted environment | Some legitimate tools may require additional non-secret environment variables later. Additions must be explicit and reviewed. |
| Output bounds | stdout/stderr are bounded with head-and-tail retention; the full text is spilled to `.odessy/spill/` and replaced inline with a preview, an exact omitted-byte count, and a locator | Truncation is no longer lossy, but bounded is not the same as sanitized. See the credential handling row below for what is and is not redacted. |
| Credential handling | Policy is **defined but not enforced**; name-based redaction covers **both** terminal executors (Python, and Node since v0.3.0) and, since v0.4.0 development, every MCP tool result at the observation boundary, including file reads, search matches, Git text, and credential-named fields | There is no credential store, vault, or reference resolver. Detection is name-based and misses unrecognised secret shapes in unnamed fields, and a credential written by a tool's own side effects is outside the returned-result boundary. See `docs/security/credential-handling.mdx`. |
| Data egress | Local inference avoids model-provider requests. Configured external HTTP servers receive their tool-call arguments; stdio server programs may perform their own I/O. Cloud backends send the user's text and redacted tool observations to their provider. | A local model does not guarantee local-only data flow when external tools are configured. Cloud redaction is best effort, and there is no comprehensive egress policy for external servers. See `docs/reference/cloud-models.mdx` and `docs/reference/external-servers.mdx`. |
| MCP server exposure | Node HTTP transport is intended for local/controlled use | There is no production authentication layer for a LAN-exposed MCP endpoint yet. Prefer loopback or SSH tunneling for Jetson/laptop development. In the `single` deployment the server binds loopback on a random free port for the length of one run, but it is still unauthenticated: another process on the same computer could call it during that run. |
| Single-machine degraded mode | Without Node dependencies, `single` mode mounts and advertises only time, calculator, and the Python `terminal.run` | That `terminal.run` has no confinement backend (Odessy passes it none), so commands run unconfined and each result reports `enforcement: "none"`. Installing the Node tool server restores its backends. |

## Isolation Layer

v0.3.0 adds provider-selected confinement. The backend is chosen by **what the host can
actually enforce**, not by platform name, and every run reports what it achieved.

Every executor routes commands through `confine()`, including runs with no backend
configured, so a run **states** its enforcement rather than leaving it to be inferred.
`required` isolation can never be satisfied by a mode providing no confinement — not by
selection, not by escalation, not by omission.

| Backend | Platform | Coverage here |
|---|---|---|
| `bwrap` | Linux | The only backend with a real chance of confining on this board, if installed and functional. |
| `landlock` (Python) | Linux | **Unavailable.** Landlock is off in this kernel (`CONFIG_SECURITY_LANDLOCK is not set` in L4T — a kernel decision, not a runtime toggle), and Odessy ships no `landlock-run` launcher. |
| `landlock` (TypeScript) | Linux | **Unavailable.** Node cannot issue `landlock_create_ruleset`, so the ABI is reported as *unknown* rather than guessed. |
| `seatbelt` | macOS | Available on macOS. |
| `windows-acl` | Windows | Available, and **`partial`** by construction — see below. |
| `unconfined` | any | Not a backend: the named, reported absence of confinement. |

### What this does not mean

Implementing the layer does **not** confine the Jetson. On this board most backends
report unavailable, which is the intended behaviour — an unavailable backend is a fact
the report states, not a failure to conceal.

```text
Allowed        "Odessy has an isolation layer; its coverage depends on the host, and
                each run reports what it achieved."
Not allowed    "Odessy is sandboxed", "jailed", or "contained" -- without the
                qualifier, because on this board it would be false.
```

### The Windows backend's named gaps

`windows-acl` reports `partial` rather than overstating its boundary:

1. `WRITE_RESTRICTED` must retain `Everyone` for process initialisation, so an external
   object whose DACL grants Everyone a write right stays writable.
2. NTFS hard links alias a *file object*, so a granted workspace file is writable
   through an external alias.

Reads, network, and process visibility are **not** restricted on Windows.

### Not isolated at all

- **Host pairing does not exist.** Single mode launches a local subprocess; split
  mode supports configured remote MCP URLs without authenticated pairing. v0.4.0
  pairing work waits on a concrete trust scenario and adversary model. A server
  must be explicitly marked an `ExecutionTarget` before anything will execute on it.
- **No device backend exists.** ESP32 / STM32 / RP2040 are declared and unbacked.
- **No hard real-time guarantee anywhere.** The Linux host is upper-tier compute and
  control planning; a device that needs a deadline owns it in firmware.

Full inventory of declared-but-unbacked capability:
`docs/execution/PROVIDER-PLACEHOLDERS.md`. Timing: `docs/execution/REAL-TIME-BOUNDARY.md`.
Design detail (internal record, outside this docs set):
`../docs/execution-layer-design.md`.

## Tooling Limits

| Tool area | Current state | Limitation |
|---|---|---|
| `terminal.run` | Workspace-cwd-bound, policy-gated, sanitized env, timeout, output caps | It still invokes a shell, so policy cannot perfectly infer all command behavior from text. |
| Read-only Node tools | `filesystem.read`, `filesystem.list`, `project.find`, `project.grep`, Git read-only tools | They are useful for project understanding, but they are not a broad file manager or search platform. |
| Git tools | Fixed-argv read-only commands | Git output is redacted, captured and bounded, and the full output is recoverable from a spill locator. Redaction is best effort: an unrecognised secret shape is not caught. |
| Schema validation | Basic MCP schema validation in the Python loop | Validation is intentionally small and type-focused. It does not yet implement full JSON Schema semantics. |
| Observations | Structured tool result objects | Every observation is redacted before exposure and before logging, since v0.4.0 development. Output from both terminal executors (`terminal.run` in Python; Node uses `terminal.run` in single mode and `laptop.terminal.run` in split mode, since v0.3.0) is redacted before retention and before spill; file content and Git text use the same pipeline. Large outputs are bounded and recoverable rather than truncated away. |

## Jetson Voice Benchmark Limits

October 20 manual smoke tests reached transcription, model execution, and
speaking in fake-model and auto wake sessions. These used a board-local Silero
VAD frame-size correction; the repository adapter now includes the explicit
512-sample setting and a hardware-free regression test. A fresh Jetson test of
the synced repository fix remains pending.
The Q8 test profile (15 GPU layers, batch 64, context 1024) also experienced
intermittent CUDA allocation failures. Spoken `Hi` followed by visible LFM
residency remains unexplained without transcript/history/escalation evidence;
successful text answers do not establish route correctness. See the
[Jetson procedure](../jetson-wake-testing.md) and
[routing observations](model-selection.mdx#routing-boundary-and-october-20-jetson-observations).
No new latency, detection-rate, or memory-stability benchmark is established.

Odessy has started voice feasibility benchmarking on Jetson Orin Nano Super 4GB and now has an initial staged voice interface in code.
The benchmark result is not yet the same as a manually verified Bluetooth voice demo.

Current benchmark status:

| Component | Current result | Limitation |
|---|---|---|
| Whisper.cpp STT | CPU-only `ggml-tiny.en.bin` transcribes an 11-second sample in about 1.1 to 1.6 seconds | CUDA Whisper currently fails during cuBLAS resource allocation, so CPU-only STT is the baseline -- established in v0.2.0, unchanged in v0.3.0. |
| LFM2.5-Thinking | Runs through Ollama with native tool calls on the Jetson baseline | Its latency, token rate, residency, and memory/swap behavior still need systematic benchmarking. |
| Kokoro TTS | ONNX int8 model runs on Jetson and can generate speech | Measured generation is about 14.8 seconds for 5.7 seconds of audio, about 2.6x real time. The figure is a v0.2.0 measurement and is still the current one. Acceptable for feasibility, but not natural low-latency speech. |
| Full voice stack | STT, LFM, and TTS have completed staged live turns | The staged turn-based pipeline established in v0.2.0 remains the design: STT + LFM + TTS are not required to stay active in parallel. |
| Voice implementation | `python -m odessy voice` wires recording, STT, runtime, TTS, and playback | The command still depends on configured local binaries, model files, audio devices, and a real Jetson manual run. |
| Continuous microphone capture | **Implemented in v0.4.0 development, unreleased.** `odessy voice --listen` keeps one capture stream open for the session and detects the wake phrase on this machine | The microphone is open continuously while listening, and wake detection is local. **Not qualified on hardware:** open-speaker use needs echo cancellation and is not claimed, and a headset test recording detection rate, false activations, and interruption latency has not been run. Only a Linux/Jetson audio path exists; the recorder and player default to `arecord`/`aplay`. Model weights are CC BY-NC-SA 4.0 and never in the repository. |
| Blank audio handling | **Implemented in v0.4.0 development, unreleased.** Empty transcripts, known non-speech markers (`[BLANK_AUDIO]`, silence, music, or inaudible in matched brackets/parentheses), and punctuation-only text return `blank` before any model call | Unknown bracketed text and speech outside known markers are preserved. STT failures remain failures. `ODESSY_VOICE_BLANK_RETRIES` (default 2; 0 disables retries) controls fresh recordings, including actual empty STT output. **Not yet validated on real audio hardware.** |
| Conversation memory | **Implemented in v0.4.0 development, unreleased.** A session keeps up to 6 exchanges (8000 characters) in process so a follow-up ("and then?") has context | Memory is per session and never written to disk. Turns pass through the existing `redact_text` filter, which has minimum lengths: an assignment value shorter than 6 characters, or a recognised key shape shorter than 16 characters after its prefix, is left intact and resent to the model on later turns. `tests/test_wake_session.py::test_memory_keeps_a_short_secret_below_the_filter_floor` pins that behaviour as a recorded limitation. |

### Blank Audio Failure Evidence

Observed during live Jetson voice testing:

```text
python -m odessy voice
Recording started
Recording stopped
Transcribing speech
Model is thinking
MCP transferring if a tool is needed
Odessy needs confirmation to run terminal.run.
Risk: medium
Reason: terminal.run requires confirmation because the command is outside the low-risk allow rules
Arguments: {'command': 'BLANK_AUDIO', 'cwd': './', 'timeout': 5}
Allow this tool call? [y/N] N
Transcript: [BLANK_AUDIO]
Voice turn failed with status failed: Policy requires confirmation before execution: terminal.run requires confirmation because the command is outside the low-risk allow rules
```

A second run again transcribed `[BLANK_AUDIO]`; when the user allowed the command, Odessy entered the tool-observation/final-response path and was manually interrupted with `Ctrl-C`.

This was a known limitation, first recorded in v0.2.0, open through released
v0.3.0, and **implemented in v0.4.0 development, unreleased**. The evidence is kept as the record of
what the fix addresses. The behaviour it required is now enforced, and asserted by
tests that fail if a blank turn reaches the model:

```text
[BLANK_AUDIO] or empty transcript
-> does not call the model
-> cannot reach MCP, because nothing is proposed to authorize
-> returns status "blank" and the caller offers a retry
```

## Testing Limits

### Agent evaluations and provenance

`evals/` has 56 cases, including 18 hard cases, and supports local and cloud models. It runs the real agent
loop against a recording execution server, so shell commands and requested writes
are not performed on the host. It measures proposals, policy decisions, tool
sequences, and deterministic checks against fixtures. It does not measure real
shell success, host confinement, audio quality, or production safety.

The October 18 artifacts record local LFM routing-on and routing-off sweeps, plus
a separate `deepseek-flash` reference. Local multi-step pass rates were 0%; the
cloud reference passed 17/18 multi-step attempts. Multi-tool continuation should
therefore not be described as universally inactive. These observations do not
establish a routing improvement across different models. See
[the eval guide](../../evals/README.md) for results and denominators.

New run metadata adds `git_commit_note`, retaining failure details and a labeled
source-tree hash when Git is unavailable. The two older local artifacts still
have unknown revisions. The hash covers Python sources under `src/odessy`, not
the eval definitions, configuration, or dependencies; a Git commit does not
capture dirty status either. Reasoning effort and endpoint are not recorded in
metadata, so a label such as `deepseek-low` is not independent proof of the
request configuration. The Markdown summary omits the provenance note; inspect
`metadata.json`.

DeepSeek effort forwarding and reasoning-content retention have focused adapter
tests. The October 18 local verification passed 119 tests across
`tests/test_cloud_model.py` and `tests/test_evals.py`; this is not a full-suite
count or live coverage of every provider.

| Area | Current state | Limitation |
|---|---|---|
| Python tests | Latest recorded local Windows full suite on 2026-10-19: 821 passed, 3 skipped | Local verification is not proof of all hosted CI jobs or Jetson hardware behavior. Tests cover important adversarial cases, not every shell or filesystem race. |
| Node tests | Latest recorded local Windows suite on 2026-10-19: 174 passed, 1 skipped; typecheck and build passed | Earlier counts are historical. Process tests require child-process permissions; these results do not establish every Node/OS matrix outcome. |
| Process cleanup tests | Timeout result is tested | Tests verify timeout reporting, but do not deeply inspect every possible descendant-process cleanup scenario. |

## Architecture Limits

Odessy is currently designed for:

```text
single user
local workspace
command-line tools
Python runtime authority
MCP tool protocol
Node laptop-side tool server
```

It is not currently designed for:

- untrusted multi-user hosting;
- public network MCP exposure;
- automatic discovery or blanket trust of arbitrary third-party MCP servers (v0.4.0 development supports explicitly configured servers only);
- production-grade sandbox isolation (v0.3.0 has a host-dependent isolation layer,
  documented above, not production-grade coverage);
- long-running autonomous jobs;
- GUI/desktop operation;
- hardware/robotics control.

## Write Tools: The Questions Step 8 Answered

This list is historical -- it was the pre-Step-8 checklist. Step 8 shipped the escalation
and isolation machinery, so the answers are recorded here as context rather than as open
work:

1. Which writes require confirmation -- decided by policy classification; anything
   outside the low-risk allow rules requires confirmation.
2. Which writes, if any, can be automatically allowed -- only those matching the low-risk
   allow rules.
3. How output redaction should work for reads, grep results, Git diffs, and terminal
   output -- both terminal executors are redacted (Node since v0.3.0), and v0.4.0
   development redacts every tool observation, including reads, grep, and Git results.
4. Whether write paths need further restrictions beyond current tool and workspace
   checks remains a policy-design question; write tools now exist.
5. How confirmation is represented so the model cannot approve itself -- the model
   requests, an `EscalationApprover` decides, and a denied `danger-full-access` request
   cannot fall back to a wider mode. In `feat/voice-user-interaction` development,
   the shared controller combines ordinary confirmation with sandbox expansion.
   Medium-risk confirmation supports the exact spoken phrase; high-risk actions
   and all sandbox expansion require keyboard or authenticated UI. No spoken
   identity or replay-resistance assurance is claimed. Bounded clarification and
   pending-question API controls have offline coverage; real microphone/Jetson
   qualification remains separate. See [voice integration](voice-integration.mdx).

These limitations should be updated whenever Odessy adds Gemma, voice, write tools, public MCP exposure, or further OS-level containment. v0.3.0 added the isolation layer, and the **Isolation Layer** section above is where its coverage is recorded per host.

Where this page still names an earlier version -- for example the Jetson voice benchmark
figures measured in v0.2.0 -- the version is stated so the claim is not read as a fresh
v0.3.0 measurement.
