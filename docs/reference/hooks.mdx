---
title: Hooks
---

A hook is a program you configure to run at a fixed point of a turn: before a
tool call, before a sandbox escalation, after a call, or when the turn has its
answer. A rule is the same idea without a program: a few lines of TOML that deny
or confirm calls matching a pattern. Use them to block a command your policy
would allow, to ask before a call outside office hours, to stop the agent sending
anything out after it read a secret, to run a linter after the model writes a
file, or to get a desktop notification.

Hooks and rules never widen what the model may do. They can deny a call or ask
for confirmation of one; they cannot allow a call the policy denies, skip a
confirmation the policy requires, or change the sandbox mode a command runs in.

## Where the file lives

`~/.config/odessy/hooks.toml`, or the path in `ODESSY_HOOKS_FILE`. It is never
read from the workspace: a repository must not be able to run programs of its
own choosing on your machine. `python -m odessy doctor` lists the hooks and
rules that apply to the current folder and warns when a hook's program cannot be
found.

Set `ODESSY_HOOKS_REQUIRED=1` to refuse to start when the file is missing, or
has no hook or rule for the workspace, instead of running without them.

```toml
[[pre_tool]]
name = "no-force-push"
match = ["terminal.run", "laptop.terminal.run"]
command = ["python", "C:/Users/me/hooks/no_force_push.py"]

[[pre_tool]]
name = "office-hours"
risk = ["medium", "high"]
command = ["python", "C:/Users/me/hooks/office_hours.py"]
on_error = "confirm"

[[post_tool]]
name = "lint"
match = "filesystem.write*"
workspace = "D:/projects/odessy"
command = ["ruff", "check", "--quiet", "."]
timeout = 20

[[turn_end]]
name = "notify"
command = ["notify-send", "Odessy finished a turn"]
```

| Key | Events | Meaning |
|---|---|---|
| `name` | all | 1-32 lowercase letters, digits, `-` or `_`; unique in the file |
| `command` | all | The program and its arguments, as a list. No shell is involved |
| `match` | all but `turn_end` | Tool-name patterns (`*`, `?`), default `"*"` (`pre_escalation`: the two terminal tools) |
| `risk` | all but `turn_end` | Policy risk levels to run for (`low`, `medium`, `high`); default all |
| `workspace` | all | Run only when Odessy works in this folder |
| `timeout` | all | Seconds, at most 60. Default 5 for `pre_tool` and `pre_escalation`, 10 otherwise |
| `on_error` | `pre_tool`, `pre_escalation` | `deny` (default) or `confirm` when the hook fails |

Each event allows at most 8 hooks. Hooks of one event run in file order.

## Protecting the hooks themselves

A hook runs as you, outside the sandbox, so the hooks are a way out of it for
anyone who can change them. Odessy guards them three ways:

- **The agent may not touch them.** A local `terminal.run` that names the hooks
  file, its folder or a hook's script is denied, and so is a `filesystem.write`
  to them. `sandbox.toml` is protected the same way, and bwrap and seatbelt hide
  `~/.config/odessy` from confined commands altogether. This holds before the file exists: an agent that created one could
  run anything it liked. (A command is text, so this is a screen, not a
  boundary; the next point catches a change made another way.)
- **A change is noticed.** The file, and every script a hook names by an
  absolute path, is fingerprinted the first time Odessy reads it. If either
  changes or disappears while Odessy runs, every tool call is denied until you
  restart it. Edit hooks with Odessy stopped.
- **Scripts live outside the workspace.** A hook whose command names a file
  inside the workspace (a relative name is resolved there) is refused at start:
  the repository could rewrite it.

## Rules

A rule runs in-process, before the hook programs, so it costs nothing per call.
Every condition a rule names must hold for it to fire.

```toml
presets = ["recommended"]

[[rule]]
name = "no-prod-deploys"
match = ["terminal.run", "laptop.terminal.run"]
command_regex = 'kubectl\s+.*--context[= ]prod'
decision = "deny"
reason = "production is deployed by CI"

[[rule]]
name = "few-writes"
match = "filesystem.write"
max_per_turn = 5
decision = "confirm"

[[rule]]
name = "mark-secret-reads"
match = "filesystem.read"
path_glob = ["*.pem", "*.key", "secrets/*"]
decision = "taint"
taint = "secret-read"

[[rule]]
name = "nothing-out-after-secrets"
match = ["terminal.run", "laptop.terminal.run"]
when_taint = "secret-read"
command_regex = '\b(curl|wget|scp|ssh|git\s+push|iwr|invoke-webrequest)\b'
decision = "deny"
```

| Key | Meaning |
|---|---|
| `name` | 1-32 lowercase letters, digits, `-` or `_`; unique among rules |
| `decision` | `deny`, `confirm`, or `taint` (mark the turn after a matching call runs) |
| `match`, `risk`, `workspace` | As for hooks |
| `command_regex` | A regular expression searched in the call's `command` (case-insensitive) |
| `arguments` | A table of argument name = regular expression, e.g. `{ task = "deploy" }` |
| `path_glob` | Globs for the call's `path`, relative to the workspace or absolute; `*` crosses folders, and a glob without `/` also matches the file name |
| `escalation` | Fire only for a call asking for one of these sandbox modes (`workspace-write`, `danger-full-access`) |
| `target` | Fire only for calls on `local` or the paired `laptop` |
| `when_taint` | Fire only once the turn carries one of these taints |
| `max_per_turn` | Let this many matching calls through each turn; the rule decides the rest |
| `taint` | The taint a `taint` rule adds |
| `reason` | Shown in the denial or approval prompt |

Rules see the arguments as the model wrote them: they never leave the process.
At most 64 rules, presets included. Taints last for one turn.

### Presets

`presets = ["recommended"]` adds rules for what most people never want an agent
to do on its own. A rule of yours with the same name replaces the preset's.

| Rule | Decision | Covers |
|---|---|---|
| `no-force-push` | deny | `git push --force`, `-f`, `--force-with-lease`, `+ref` |
| `no-pipe-to-shell` | deny | A download piped into a shell (`curl ... \| sh`, `iwr ... \| iex`) |
| `no-world-writable` | deny | `chmod 777`, `a+w`, `o+w` |
| `no-privileged-containers` | deny | `docker`/`podman run --privileged`, host namespaces, `/` mounted |
| `no-package-publish` | deny | `npm publish`, `twine upload`, `cargo publish` and friends |
| `no-git-dir-removal` | deny | Deleting `.git` |
| `no-persistence` | deny | `reg add`, `schtasks /create`, `crontab`, `systemctl enable` |
| `confirm-history-rewrite` | confirm | `git reset --hard`, `clean -f`, `rebase`, `branch -D`, `stash drop` |
| `confirm-ci-and-hooks-edits` | confirm | Writing `.github/`, `.gitlab-ci.yml`, `.git/`, `.husky/`, pre-commit config |
| `no-full-access-on-laptop` | deny | `danger-full-access` on the paired laptop |

## How a hook runs

A hook runs as you, outside Odessy's sandbox, with the workspace as its working
directory. It reads one JSON object on stdin. Its environment is a short
allowlist (`PATH`, `HOME`/`USERPROFILE`, temp and locale variables, and on
Windows `SYSTEMROOT` and friends) plus `ODESSY_HOOK_EVENT` and
`ODESSY_WORKSPACE`. API keys and tokens are not passed on. Arguments and
results are redacted the same way the turn log redacts them.

Stdout and stderr are each limited to 64 KiB while being read. Exceeding either
limit fails the hook under its existing `on_error` policy. Timeouts, cancellation
and output overflow terminate the owned process tree (a Windows Job Object or
POSIX process group), with bounded pipe cleanup. Hooks must not start persistent
background services; Windows also closes descendants when the hook exits.

### pre_tool

Runs after the policy has decided, before anyone is asked, for calls the policy
did not deny. Input:

```json
{"event": "pre_tool", "tool": "terminal.run", "arguments": {"command": "git push -f"},
 "policy": {"decision": "allow", "risk": "low"}, "workspace": "D:/projects/odessy",
 "execution": {"target": "local", "mode": "read-only", "isolation": "preferred", "escalation": null},
 "session": {"turn_id": "3f9c2a1b7d4e", "call_index": 2},
 "request": "push my branch", "taints": []}
```

`execution.mode` is the sandbox mode the policy's decision implies, before any
escalation; `escalation` is `{"requested": ..., "justification": ...}` when the
call asks for a wider mode. `request` is the user's message for this turn
(redacted, up to 2000 characters), and `taints` what rules and post-tool hooks
marked the turn with so far.

The answer:

- exit 0 and print nothing: no objection;
- exit 0 and print `{"decision": "allow" | "confirm" | "deny", "reason": "..."}`;
- exit 2: deny, with what the hook wrote to stderr as the reason;
- anything else (another exit code, output that is not a decision, a timeout,
  a program that cannot start) is a failure, decided by `on_error`. A failing
  hook never allows a call.

The strictest answer of all matching hooks wins, and a deny stops the
remaining hooks. A denied call ends the turn like a policy denial. A call a hook
wants confirmed is asked about through the usual channel, and the approval
prompt names the hook; a command the policy would have run read-only stays
read-only after you confirm it. Each call is screened once: a single call, a
call in a batch, and a call approved through the session's approval broker all
pass through the same check, and a call that reaches execution unscreened while
a hook or rule matches it is denied.

A job you start from the desktop (`/jobs`) does not pass through the agent loop;
it is screened by the same rules and pre-tool hooks before you are asked, with
`execution.origin` set to `api`.

### pre_escalation

Runs for a call that asks for a wider sandbox (`sandbox_permissions`), after its
pre-tool checks and before the human is asked about the escalation. Input adds
`"escalation": {"requested": "danger-full-access", "justification": "..."}`. Only
a deny counts: every escalation is put to a human anyway, so `confirm`, `allow`
and an `on_error = "confirm"` failure leave the decision to them. A refused
escalation ends the turn like a policy denial.

### post_tool

Runs after a call, whether it succeeded or failed. Input adds `"result"`, the
tool's structured result. What the hook prints (or `{"note": "..."}`; stderr
when it printed nothing and exited non-zero) is added to the result the model
sees, under `hook_notes`, with its exit code and a marker saying it came from
your hooks and not the tool. Notes are capped at 2000 characters each. A hook
that fails or times out adds nothing and is recorded in the turn log.

A post-tool hook can also print JSON with any of:

- `"taint": "name"` or a list: mark the turn, for `when_taint` rules and for
  later hooks (`taints` in their input);
- `"decision": "stop"`: end the turn after this call, with
  `Stopped by the <hook> hook: <reason>` as the answer;
- `"quarantine": true`: replace what the model sees of this result with a
  notice that your hook withheld it. Use it for output that looks like a prompt
  injection. The result itself stays in the turn log (`hook_quarantine`).

`reason` goes with any of them.

### turn_end

Runs in the background once the turn has its answer, so the answer is not held
up. Input: `outcome` (`answered`, `stopped` or `error`), the `request`, the
`final_text` (each up to 2000 characters) and the `tools` that ran. Output is
ignored.

## Events and logs

Every hook and rule decision, note and failure is in the turn log
(`hook_decision`, `hook_note`, `hook_failed`), with `hook_taint`, `hook_stop`
and `hook_quarantine` for the post-tool actions. A third-party tool's audit
record carries the deciding rule, `hook:<name>`, when a hook or rule decided.

## Delegated agents

A coding CLI started with `agent.delegate` (Codex, Claude Code, a custom agent)
runs its own tools, and Odessy's hooks cannot see inside it. Odessy launches
Claude Code with `--bare`, which skips Claude Code's own hooks too. So the
delegation is screened at both ends instead: the `agent.delegate` call goes
through the rules and pre-tool hooks like any other call, and when the job
finishes the files it changed are checked against your `filesystem.write` rules
as if Odessy had written them. A finding marks the job `needs_attention` with
`hook_review` (`blocked` for a deny, `confirm` for a confirm) listing the files
and rules; a review that cannot run blocks the job rather than passing it. The
job's `permissions.hooks` says which applies.

The session API also streams what happens inside a turn as it happens:
`tool` events (`started`, `finished` with its status), `policy` events (the
outcome and risk of each call), `hook` events, and `final_call`. These carry
names, call ids and outcomes only; arguments, results and reasons stay in the
turn log because a reason can quote an argument.
