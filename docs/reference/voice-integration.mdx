Development voice sessions share the controller with CLI and HTTP. `switch model to <profile>` selects the next turn; `consult <participant>: <question>` requests attributed advice. Stop does not undo completed actions. See [model collaboration](model-collaboration.mdx).


Odessy v0.2.0 added voice as an interface around the existing runtime; it is unchanged in v0.3.0.
Voice does not replace the policy, MCP, workspace authority, process authority, or confirmation path.

## Development: approval and clarification

Voice dependencies and model weights retain separate licenses. In particular,
Hey Jarvis pretrained weights are noncommercial CC-BY-NC-SA-4.0, while
openWakeWord code is Apache-2.0. Kokoro/Whisper and the GPL phonemizer dependencies
are detailed in the [third-party license inventory](third-party-licenses.md).
Custom Odessy wake-word support targets v0.5.0; v0.4.0 keeps Hey Jarvis.

The `feat/voice-user-interaction` worktree extends the shared session controller.
Both wake sessions and one-shot voice support human clarification and one-use
approval. **Offline implementation and independent review are complete as of
October 22, 2026**; the feature merged into `develop` via PR #24 (`6d8b80b`) and
is released in v0.4.0. Independent review reran **72 relevant tests, all passed**.
DeepSeek reported **1,449 passed, 5 skipped** for the full suite; that full count
was not independently repeated. Real microphone, Jetson and packaged-device
qualification remain pending, separate opt-in checks.

October 23 follow-up: real Jetson/JBL wake and spoken-reply smoke tests completed.
Five recorded WAVs through actual Whisper and the session/broker verified exact
medium approval, bare-yes refusal, high-risk/escalation refusal, natural denial,
cancellation and free-text clarification. Updated phrase regressions and voice
integration checks: **155 passed**. Physical playback echo/pre-cue admission,
the deferred one-hour false-activation run and packaged-device acceptance remain
unqualified. Echo/pre-cue checks test Odessy's capture/admission integration,
not the TTS/STT provider in isolation. See the
[qualification results](../qualification/2026-10-23-interactions-and-pairing.md).

Deployment acceptance decision (October 23): defer the physical echo/pre-cue
trials until the complete software is deployed. Software timing/isolation
regressions pass; physical response-admission behavior and open-speaker operation
are not yet qualified. This deferral does not block ongoing development.

| Policy decision | Accepted approval channels |
| --- | --- |
| Allowed low-risk action | Existing policy; no new prompt |
| Medium-risk confirmation | Exact spoken phrase, keyboard, authenticated UI |
| High-risk action or any sandbox expansion | Keyboard or authenticated UI only |
| Denied action | None; confirmation cannot override denial |

Denial accepts whole-response variants including **I deny**, **don't do that**,
**no thanks**, and **please reject this**. Cancellation accepts **stop this**,
**cancel that**, and **please stop**, alongside stop/cancel/never mind. These
deterministic phrases are shared by wake, one-shot voice, and typed pending replies;
they are not model-inferred permissions. Negations such as **don't stop** do not
cancel. Clarification remains free text or an explicitly restricted choice.

For eligible approval, say **approve this action** after the cue. Bare yes,
spoken session grants and spoken approve-all are unsupported. The phrase is
shown on screen but never spoken in a pending prompt. Voice indicates intent;
it does not authenticate a speaker or resist recording replay. See the
[authority boundary](authority-boundary.mdx) for the grant checks.

Authorization begins “Odessy requests permission…” and displays the validated
operation, execution host, exact command/arguments, scopes and accepted channels.
Clarification begins “I need one detail…”; its answer provides information only.
A stronger-channel request remains pending for keyboard/UI confirmation.

There is one microphone reader in wake mode. Prompt playback and queued pre-cue
audio cannot supply a response. Capture opens after settling and the cue. A fresh
wake supersedes the pending interaction and starts replacement capture. Stop,
cancel and shutdown invalidate outstanding replies; completed tools remain done.

Defaults are three clarification requests per turn, two STT reprompts, a 30-second
response window, and 120 seconds for keyboard/UI-only approval. Reprompts do not
extend expiry or consume clarification requests. A missing answer ends the turn
explicitly. Human waiting is excluded from the optional generation deadline;
independent operation timeouts keep their original bounds.

| Environment setting | Default | Accepted values |
| --- | --- | --- |
| `ODESSY_INTERACTION_MAX_QUESTIONS` | 3 | integer 1–20 |
| `ODESSY_INTERACTION_RESPONSE_TIMEOUT` | 30 seconds | greater than 0, at most 300 |
| `ODESSY_INTERACTION_STRONG_RESPONSE_TIMEOUT` | 120 seconds | greater than 0, at most 600 |
| `ODESSY_INTERACTION_PROMPT_TIMEOUT` | 30 seconds | greater than 0, at most 120 |
| `ODESSY_VOICE_SETTLING_MS` | 300 ms | integer 0–10000 |

The initial prompt timeout bounds cue preparation; the response window starts
once capture is ready. Text CLI uses cancellation-safe terminal input and one-use confirmations through the shared controller. Redirected
or unavailable interactive input fails explicitly; the HTTP service supports
an authenticated UI instead. Background jobs, status, events and API responses
remain responsive while a foreground turn waits.

## Architecture

### Development: session-preserving keyboard input

TTY voice commands now compose `HybridConsole` and `HybridAudioAdapter` over the
existing controller. One keyboard reader serves requests, approvals and questions;
the controller remains the sole owner of history, selected models and permissions.
Try `python -m odessy voice --listen --fake-model`, then type a follow-up.
One-shot `voice` opens recording immediately and exits after its first reply.

`/text` pauses capture admission and speech without cancelling model/tool work.
`/voice` explicitly retries audio; `/stop` cancels the owning turn; `/exit`, EOF
and Ctrl+C close the session. Typed answers are displayed; voice answers are
displayed and optionally spoken. Busy requests are rejected, never queued.
Audio failures never retry inference or tools. Missing audio-only assets can
degrade to keyboard input; invalid model/policy settings still fail startup.
Voice-mode model-call limits continue to apply to typed fallback turns.

Wake/VAD loading, audio factories and device startup run off the event loop.
`/voice` retries in the background while the keyboard remains available. Input
pause is rechecked after opening the device, and rapid `/text` then `/voice`
commands preserve the latest requested mode without competing initializers.

Pending human replies go through the same broker and exact-phrase/channel checks.
Changing prompt ownership cancels the old keyboard read and discards buffered
input. High-risk actions still require keyboard or authenticated UI; fallback
cannot override policy denial. Existing authenticated HTTP endpoints are unchanged.
Use `--no-text-fallback` for legacy audio-only behavior. Non-TTY stdin is not read
as requests or approvals. Real terminal buffering, microphone echo and Jetson
operation remain separate qualification; fake-I/O tests do not establish them.

The staged voice turn is:

```text
bounded audio recording
  -> Whisper.cpp CPU-only STT
  -> transcript text
  -> existing Odessy agent loop
  -> policy/MCP/tool handling if the model proposes a tool
  -> final response text
  -> Kokoro ONNX TTS
  -> audio playback
```

The required authority invariant remains:

```text
Model proposes.
Runtime validates.
Policy decides.
MCP transports.
Tools execute only after authorization.
```

The voice layer must not execute tools directly.

## Run Command

After installing the package in editable mode:

```powershell
pip install -e .
```

Then run:

```powershell
python -m odessy voice
```

For local testing without a live model backend:

```powershell
python -m odessy voice --fake-model
```

Voice mode accepts the same `--model-backend` selection as the text loop, so a cloud
backend can be used here too:

```powershell
$env:ODESSY_CLOUD_MODEL="deepseek-flash"
$env:ODESSY_CLOUD_EFFORT="low"
python -m odessy voice --model-backend deepseek
```

This example uses the same low-effort setting as text mode and evals. The adapter
retains returned reasoning content when continuing tool conversations. This
one-shot example does not enable streamed speech; development wake sessions with
`--listen` support the streamed path described below. No latency gain is measured.

With a cloud backend the transcript and that turn's tool observations leave the machine.
The voice pipeline itself is unchanged — the same authority invariant and the same
tool path still apply. See `docs/reference/cloud-models.mdx` for the data flow and limits.

The existing text loop remains available:

```powershell
odessy voice
odessy-loop "calculate 12 * 8"
```

## Configuration

Voice mode is configured through environment variables.
Device names are intentionally not hard-coded.

```text
ODESSY_WHISPER_BIN      path/name of whisper-cli
ODESSY_WHISPER_MODEL    path to ggml-tiny.en.bin or another Whisper model
ODESSY_KOKORO_MODEL     path to kokoro-v1.0.int8.onnx
ODESSY_KOKORO_VOICES    path to voices-v1.0.bin
ODESSY_MODEL_BACKEND    local (lfm|ollama|llama_cpp), auto, or a cloud provider; default lfm
ODESSY_OLLAMA_MODEL     Ollama model name used by voice mode; default config uses LFM2.5-Thinking
ODESSY_MODEL_NAME       Default LFM model name, lfm2.5-thinking:1.2b-q8_0
ODESSY_MODEL_ENDPOINT   Ollama endpoint, default http://127.0.0.1:11434
ODESSY_TOOL_SERVER_URL  Optional laptop-side MCP HTTP endpoint
ODESSY_AUDIO_RECORDER   recorder command, default arecord
ODESSY_AUDIO_PLAYER     player command, default aplay
ODESSY_AUDIO_INPUT_DEVICE
ODESSY_AUDIO_OUTPUT_DEVICE
ODESSY_VOICE_SECONDS    bounded recording duration, default 5
ODESSY_VOICE_BLANK_RETRIES  v0.4.0: extra recordings for no speech; default 2, 0 disables retries
ODESSY_VOICE_TMPDIR     controlled temporary audio directory
```

## Jetson Baseline

Whisper.cpp should use CPU inference with `-ng` (the v0.2.0 baseline, still current).
CUDA Whisper remains a separate unresolved optimization because the benchmark saw cuBLAS resource-allocation failure.

Kokoro ONNX int8 works on the Jetson but is slow in the current benchmark:

```text
about 14.8 seconds generation for 5.7 seconds of audio
about 2.6x real time
```

This latency was accepted for v0.2.0 because the priority is a working local voice loop before optimization. The figure is a v0.2.0 measurement, not a fresh v0.3.0 one.

## Wake-Word Sessions

Merged into `develop` in the v0.4.0 release cycle. For Linux installation,
support-model setup, audio checks, and a staged real-device test, follow the
[Jetson wake test guide](../jetson-wake-testing.md). Automated CI does not qualify
the Jetson microphone, detector, or playback latency.

October 20 user-reported Jetson runs reached transcription, model execution,
and speaking with fake-model and auto listening. The installed Silero VAD needed
a board-local `frame_size=512` correction. The repository adapter now includes
that correction and a hardware-free regression test; sync it before retesting.
A later apparent wake failure was traced by the user to
the microphone being off. Auto voice using LFM after spoken `Hi` remains an
unresolved routing observation; see the
[routing boundary](model-selection.mdx#routing-boundary-and-october-20-jetson-observations).
These smoke tests do not qualify detection rate, interruption, or shutdown.

`odessy voice --listen` keeps the microphone open, waits for a wake phrase, and then
runs exactly the same turn as a typed request. The existing single bounded turn is
unchanged; `--listen` selects the session controller instead of one recording.

```powershell
odessy doctor --voice            # check what the wake session needs, without opening it
odessy voice --setup-wake        # fetch and record the model assets, then exit
odessy voice --listen            # wake phrase before every request (default)
odessy voice --listen --interaction conversation
```

The interaction is: say the wake phrase, wait for the ready cue, then speak. During a
reply or a task, say the phrase again to interrupt; after the cue, "stop", "cancel" or
"never mind" is handled locally without calling the model, and anything else becomes
one pending replacement request that runs after the previous turn settles.

`--setup-wake` installs Odessy's pinned keyword model. openWakeWord's feature and
Silero VAD resources must also exist in the active environment; the Jetson guide
documents their explicit upstream download and a detector-initialization check.
Doctor does not load both detectors and cannot establish that these files work.

| Interface | Behaviour |
|---|---|
| `odessy voice` | One bounded turn, exactly as before |
| `odessy voice --listen` | Continuous wake listening |
| `--interaction wake` | The phrase is required before every request (default) |
| `--interaction conversation` | A short follow-up window stays open after each reply |
| `odessy voice --setup-wake` | Downloads and records the default model assets, explicitly |
| `odessy doctor --voice` | Reports the detector, model, and device state without opening the microphone |

Settings: `ODESSY_VOICE_INTERACTION` (`wake`\|`conversation`, default `wake`),
`ODESSY_WAKE_MODEL`, `ODESSY_WAKE_THRESHOLD` (default `0.5`),
`ODESSY_VOICE_FOLLOWUP_SECONDS` (default `10`), and
`ODESSY_VOICE_MAX_UTTERANCE_SECONDS` (default `20`). An invalid value stops startup
with a message naming the setting.

### How the session is built

One long-lived `arecord` process owns the microphone for the whole session, producing
16 kHz mono signed 16-bit PCM. Its frames are re-cut per consumer: 80 ms for wake
detection, 32 ms for the VAD, because the two models have different frame sizes and
re-recording for each would be wrong. A wake event discards the pre-cue buffers,
plays a short cue, and only then opens capture, so cue audio is never part of a
request.

The session is *one reader and one worker*. The reader never blocks on a model call,
which is why the wake phrase still works while a turn executes or a reply plays. The
worker runs one turn at a time; two model generations never overlap on one adapter.
Model generation itself runs in a worker thread, serialised by a lock, so the event
loop keeps reading audio.

Capture uses a bounded frame queue with explicit overflow failure. Transcription
runs separately with one active STT operation and at most one pending recording;
superseded transcripts are discarded. Activation/cancellation clears obsolete
requests. Playback generation tokens discard queued or late-starting replies.
Capture failure signals cooperative stop; closing wakes waiting tasks and closes
the source, and startup failures release the recorder. Actual Whisper `empty`
results use the same bounded blank retries. These are software behaviors covered
by regression tests, not measured real-device guarantees.

The session decides when the microphone is open and what text to submit; every
proposed action still passes validation, policy, confirmation and the
execution-target gate. Ordinary wake-command transcripts do not authorize actions.
Only a valid response to a pending, voice-eligible request can provide spoken
approval through the shared interaction broker described above.

Conversation mode keeps at most six completed exchanges and 8,000 characters in RAM,
redacted with the same best-effort, name-based filter as the rest of the runtime before
storage, cleared on exit, and never carried into a new turn as a prior approval or
tool-call identifier. Interrupted turns are not recorded.

### Streamed speech

Merged via PR #23 (`d05e1b8`) and released as an extra v0.4.0 feature.

With a cloud model, a wake-listening session speaks the answer sentence by sentence
as the reply arrives, instead of after the whole reply. The first sentence is heard
while the rest is still being generated.

- **On by default;** `ODESSY_VOICE_STREAM_SPEECH=off` turns it off. Local models do
  not stream, so nothing changes for them.
- **Text before a tool call is spoken** ("Let me check the disk"). Once a tool call
  starts in a reply, the rest of that reply is not. Speech is output only: the tool
  call still goes through validation, policy, and confirmation.
- **Interruptions still win.** The wake phrase stops playback and drops the
  sentences not yet spoken; a stopped turn says the usual stopped message.
- **No repeats.** When the turn's answer is the text already spoken, it is not said
  again. A different answer (a runtime message such as a turn limit) is spoken after.
- **A failed stream is not retried once a sentence was spoken,** so nothing is said
  twice. A consulted peer's advice is never spoken.
- Sentences are synthesized one at a time, so a short pause between sentences is the
  TTS time for the next one.

### Boundaries of this version

- **Headset first.** Listening stays active during playback, but reliable
  open-speaker operation needs echo cancellation and is not claimed.
- The contract is "phrase, then cue, then speak". A same-breath "phrase + command" is
  out of scope.
- Custom wake phrases are not supported: the default is a pretrained "Hey Jarvis"
  model, and a custom "Hey Odessy" phrase needs its own training run.
- **Model weights are not Apache-2.0.** The openWakeWord code is Apache-2.0; its
  bundled pretrained models are CC BY-NC-SA 4.0, which forbids commercial use. They
  are never in this repository and are fetched only by `odessy voice --setup-wake`,
  which verifies the pinned SHA-256 and records source, version, checksum, and
  license next to the file. A digest that cannot be pinned is reported as
  *unverified* rather than implied to be verified.
- Qualification targets — at least 90% detection over 50 spoken activations, at most
  one false activation per hour of background audio, and p95 playback interruption
  within one second of finishing the phrase — are **acceptance targets, not
  measurements**. None of them has been measured on hardware.
- Wake activation alone promises no faster answers: the Jetson's model and TTS
  latency are unchanged and remain visible.

## Current Limits

The v0.3.0 private prerelease retains these limits. Blank-audio handling is
implemented; wake-up activation is implemented in software and awaiting hardware
qualification. Risk-aware voice approval and clarification are complete offline
and merged into v0.4.0; hardware acceptance remains pending. Further
voice/local-model optimization remains measurement-led follow-up in the
[v0.5.0 roadmap](../releases/v0.5.0.md), not a promised speedup.

Voice mode is staged and turn-based unless `--listen` is used.
Local and non-streaming replies are synthesised in full before playback.
Development cloud wake sessions can instead synthesize and play one sentence at a
time as model text arrives. This is not continuous audio-token TTS or a measured
real-time guarantee; real microphone and Jetson acceptance remain pending.

The ordinary automated tests use fake audio/STT/TTS components.
A real Bluetooth headset test must still be run on the Jetson environment before claiming the physical voice loop is complete.
