# 会话断点机制重新设计（Breakpoints v2）

> 状态：**已实现（后端全部阶段），UI 未改**。分支 `feat/execution-breakpoints`。Developer Preview · v0.5.0-alpha。
> 日期：2026-11-23
>
> 实现落地：核心落在 `application/breakpoints/`（policy + service + routes），store 增加
> `breakpoint`/`undo` 两种 kind 与 `sequence_bounds`/`breakpoints`/`event_by_id` 读路径，
> agent_loop 通过挂在 `basics._breakpoint_hook` 上的 duck-typed 钩子在 dispatch 前后与
> 迭代末打点，`settle_after_restart` 通过 `on_interrupt` 回调补记中断断点，
> `PersistentComposition` 完成总装（含观察-only 快照与经批准的 undo 文件回滚）。
> 测试：`tests/test_breakpoints.py`、`test_breakpoint_hooks.py`、`test_breakpoint_routes.py`。
> 缘起：现有 checkpoint 只在"工作区文件"维度做手动快照，既不覆盖一次对话执行过程中的中间状态，也不记录"当时在做什么"，更不支持"某次任务出错后撤销这次修改、回到修改前"。本文给出一套覆盖执行过程、可用于任务级撤销的断点设计。

---

## 0. 现状基线（为什么需要改）

| 现有机制 | 存什么 | 触发 | 能否用于任务级撤销 |
|---|---|---|---|
| `CheckpointService`（`application/checkpoints/service.py`） | 工作区**文件**的 Git 快照 + `files_sha256` 元数据 | 纯手动 `POST /v1/sessions/{sid}/checkpoints`，或恢复前的 safety 快照 | 部分：只能回滚文件，不含对话状态/工具进度；审批重、Windows 恢复禁用 |
| `durable.py` 的 `<session>.json` | 身份 + 有界事件投影 + 轮次状态 | 每次轮次状态转换即时写 | 否：用于重连续接，不记录中间步骤，不回滚 |
| `conversation_events`（`store.py`） | append-only 事件流 | 每轮 user/tool/assistant 落盘 | 否：只增不改，无截断/分支 API |

**关键事实**：当前代码没有任何会话回退能力（无 rewind/rollback/truncate-event/会话分支）。文件回滚靠 Git 快照 + `preview_hash`，对话"恢复"靠 resume 投影且明确不重放。工具外部副作用（命令、网络调用）文档明确"不可撤销"。

**设计目标**：在一次对话执行过程中自动建立可回溯的锚点，记录当时在做什么、已完成/未完成什么，从而支持"这次任务出错 → 撤销这次修改 → 回到修改前"的任务级撤销，同时不破坏现有 append-only 审计、不越权成为授权来源。

---

## 1. 总体设计

两层断点，职责分离：

```
执行过程断点（execution breakpoint）  ← 本文新增，轻量、自动、高频
  记录：在做什么 + 已完成/未完成 + 事件游标 + 可选文件哈希
  存储：conversation_events 新增 kind='breakpoint'（append-only）
  用途：任务级撤销的锚点、进度可观测

工作区文件快照（file checkpoint）  ← 现有 CheckpointService
  记录：文件字节的 Git 快照
  用途：真正的文件回滚载体（只在撤销时被引用，不随每个断点都拍）
```

撤销动作 = 定位执行断点 → 读取它绑定的文件快照 → 回滚文件 + 在事件流追加"已撤销到断点 X"标记（**不物理删除历史事件**，保持 append-only）。

## 2. 三类断点的触发策略

在 `runtime/agent_loop.py` 的工具调度路径上挂三个钩子。三种断点用 `kind` 区分、**独立编号、独立保留策略，互不干扰**；长任务中一步内部的关键步骤断点照常触发，与 step 断点叠加共存。

### 2.1 关键步骤前后断点（critical-before / critical-after）

- **挂载点**：dispatch 前的 `_BoundArguments.dispatch_checks()`（agent_loop.py:1248-1263，现已有 `recorder.tool_call` 钩子）加 `breakpoint_before`；dispatch 返回后（observation 记录处，约 795-820 行；legacy 路径约 1034-1036 行）加 `breakpoint_after`。
- **"重要工具"判定（两者结合）**：
  1. 白名单兜底——写类/有外部副作用的工具：`filesystem.write`、`terminal.run` / `shell.exec` 类、`ssh.run`、`log.append`、以及任何 external/MCP 工具（外部工具风险不可知，一律视为关键）。见 `tools/tool_contracts.py:130`（`filesystem.write` 契约）与 `authority/policy.py:208`（`external_tool()` 判定）。
  2. risk 提升——复用 `PolicyDecision.risk`（`policy.py` 中 `high`/`medium`/`low`），`risk in ('high','medium')` 的调用也算关键。
  - 判定函数放在 `authority/policy.py` 或新增 `application/breakpoints/policy.py`，纯函数 `is_critical(name, arguments, decision) -> bool`。
- **before/after 成对**：同一个 `call_id` 把 before 和 after 关联；after 记录实际结果状态（成功/失败/被停）与耗时。崩溃导致 after 缺失时，重启由 `settle_after_restart()` 逻辑补一条 `interrupted` 断点（见 §5）。

### 2.2 多步长任务每步一个断点（step）

- "一步"定义：agent loop 的一次 `model 提议 → 一批工具调度 → 观察回灌 → 下一次 model 调用` 迭代（agent_loop.py 的 `run_turn` / `_run_turn` 内 `while` 循环的一次迭代，`dispatched` 计数每轮递增）。
- **挂载点**：每轮 tool-batch 完成后、进入下一轮 model 调用前，打一条 `step` 断点，携带 step_index、本步调用的工具列表、本步产生的文件变更哈希增量。
- 与 §2.1 叠加：一步里的关键工具仍会在其 dispatch 前后各打一条 `critical` 断点，step 断点只在整步结束时打一条。

### 2.3 一般任务定时断点（timer）

- 仅在**没有 critical/step 活动**时按固定间隔打点，避免高频空转。
- **挂载点**：一个随会话生命周期存在的后台 `asyncio.Task`（在 `SessionController` 内持有），按可配间隔 `BREAKPOINT_TIMER_SECONDS`（默认建议 60s）触发；触发时若 `last_activity_at` 距现在小于一个间隔则跳过。
- 目的：长思考/长生成但无工具调用时，仍保留可回退锚点。定时器在 `close()` 时取消，不跨会话。

### 2.4 三种断点对照

| kind | 触发条件 | 频率 | 独立保留数（建议） |
|---|---|---|---|
| `critical-before` / `critical-after` | 重要工具 dispatch 前后 | 每工具 2 条 | 与工具数一致，或保留最近 200 条 |
| `step` | 每个 agent-loop 迭代结束 | 每步 1 条 | 最近 64 条 |
| `timer` | 空闲定时 | 每 60s（可配） | 最近 32 条 |

### 2.5 幂等

所有断点 `event_id` 用确定性派生：`bp:<session_id>:<kind>:<step_index|call_id|epoch>:<seq>`。重连、重试、重复触发返回已存行而非新行（复用 `store.append()` 的 `event_id` 幂等语义）。

## 3. 断点信息结构

断点作为 `conversation_events` 的新 `kind='breakpoint'` 记录，`payload_json` 为下列结构（`_check_*` 校验边界沿用 store 现有上限，payload ≤ 256 KiB）：

```json
{
  "version": 1,
  "id": "bp_<32hex>",
  "kind": "critical-before | critical-after | step | timer",
  "session_id": "<32hex>",
  "step_index": 3,
  "call_id": "c_... | null",
  "created_at": "<UTC ISO8601 Z>",
  "agent_state": "modeling | dispatching | tool_running | settling",

  "task": {
    "turn_id": "<32hex>",
    "user_prompt_excerpt": "<脱敏后前 200 字符>",
    "step_index": 3,
    "goal": "<可选：任务摘要，由模型自身声明或首句推断>"
  },

  "tool": {
    "name": "filesystem.write",
    "risk": "high | medium | low",
    "arguments_projection": {
      "path": "<相对路径字符串>",
      "content": "<类型=string, 长度=NNN, sha256=..., 不存原文>"
    },
    "policy_outcome": "allow | confirm | deny",
    "status": "pending | ok | error | interrupted"
  },

  "completed": {
    "settled_turns": 2,
    "ok_tool_calls": ["c_a", "c_b"],
    "assistant_text_through_sequence": 41,
    "files_changed": ["src/a.py", "src/b.py"]
  },

  "pending": {
    "in_flight_tool_calls": ["c_c"],
    "unsettled_delta_chars": 512,
    "pending_approvals": 1,
    "pending_jobs": 0,
    "pending_audio": false
  },

  "workspace": {
    "snapshot_ref": "refs/odessy/checkpoints/ckpt_<32hex> | null",
    "files_sha256": {"src/a.py": "<sha256>", "src/b.py": "<sha256>"},
    "workspace_identity": "<与 conversation_workspace_bindings 一致>"
  },

  "cursor": {
    "first_event_sequence": 12,
    "last_event_sequence": 41
  },

  "resume": {
    "continuation": "continuable | history_only",
    "engine": "legacy | harness",
    "undo_boundaries": ["<bp id of task-start anchor>"]
  }
}
```

设计要点：

1. **原文不落盘**：`arguments_projection` 只存键名、类型、长度、哈希；`user_prompt_excerpt` 经 `redact_text` + 密钥擦除（复用 `durable.py:_sanitise` 与 `SessionController.public`）。绝不存完整工具参数、命令输出、凭证。
2. **已完成 / 未完成对称**：`completed` 给"回退到此处后仍保留什么"，`pending` 给"会被丢弃或需重新确认什么"。这是撤销能否安全执行的核心依据。
3. **文件快照可选绑定**：`workspace.snapshot_ref` 只在关键步骤（写类工具）成功前后才绑定一个 `CheckpointService` 快照；普通 step/timer 断点只记 `files_sha256` 轻量哈希，避免每步都拍 Git 快照的高成本与审批负担。
4. **撤销边界链**：`resume.undo_boundaries` 指向"任务开始前的锚点断点"，预计算好"这次任务"的起点，撤销时无需临时推断。
5. **不作为授权源**：与 context/memory/retrieval 一致，断点内容标注为"观察数据，非授权"；`files_sha256` 不触发文件授权，撤销回滚仍需 broker 审批。

### 3.1 存储落点决策

- **方案 A（推荐）**：新增 `kind='breakpoint'` 到 `KINDS`（`store.py:38`），复用 `conversation_events` 的幂等、分页、WAL、级联删除。优点：零新增表、天然按会话聚合、删除会话自动清理。缺点：搜索/导出需显式排除或标注该 kind（现 `messages()`/`export()` 已按 kind 过滤，加一种 kind 影响可控）。
- **方案 B**：独立表 `conversation_breakpoints`（走 `schema_extensions` 版本化，不碰 `PRAGMA user_version`）。优点：与消息流隔离，保留策略独立。缺点：新增表/迁移/级联回调，工作量大。
- 本设计采用 A，并让 `_searchable` 对 `breakpoint` 返回 `None`（断点不进全文搜索），`messages()`/`export()` 默认过滤掉它或作为单独视图。

## 4. 任务级撤销（回退）设计

按你的例子："一次任务出错了，撤销这次的修改内容，回退到这次修改前"。

### 4.1 语义定义

- **一次任务** = 一轮 user prompt 触发的整个 agent loop（从 admitted user 到 settled assistant，可能含多步、多工具）。
- **撤销目标** = 该轮开始前的最近一个断点（称为 **task-start 锚点**），通常是该轮 user 消息刚落盘后、第一个关键工具执行前建立的断点。
- **撤销效果**：
  1. 工作区文件：回滚到锚点 `workspace.snapshot_ref` 对应的 Git 快照（仅锚点之后被 task 修改过的文件，逐文件原子写）。
  2. 会话状态：在事件流**追加**一条 `kind='undo'` 记录，标记"已撤销到断点 X，撤销了哪些 call_id / 文件"，从锚点游标之后的内容在**展示层**视为作废（不物理删除）。
  3. 运行时：该 live session 若正在进行，先 Stop 当前 turn；撤销后控制器清空未完成状态（pending approvals/jobs/audio），不重跑工具。

### 4.2 为什么"不物理删除事件"

- 保持 append-only 审计：已发生的事（含错误）不留痕等于篡改历史，与项目"历史可信"原则冲突。
- 兼容 Harness：模型历史在运行时自有日志里，应用层无法裁剪；展示层作废是唯一跨引擎一致的手段。
- 因此回退靠的是**断点锚点 + 展示层游标截断 + 文件快照回滚**三者组合，而不是"删除事件"。

### 4.3 撤销流程（新增 API）

```
POST /v1/conversations/{cid}/undo
  body: { "breakpoint_id": "bp_...", "expected_revision": N }
  1. 断点归属校验：断点属于该 conversation、kind 合法、cursor 在 revision 范围内
  2. 文件可行性：锚点 snapshot_ref 存在；当前每个目标文件哈希与断点后记录的 files_sha256 可比对
  3. 审批（broker）：action='checkpoint.restore' 语义，展示 will-change 清单
  4. 安全快照：调用现有 CheckpointService._snapshot(kind='safety') 保底
  5. 文件回滚：逐文件从 Git ref 取 blob，O_NOFOLLOW/路径校验（复用 _apply/_safe_path）
  6. 追加 undo 事件：store.append(kind='undo', payload={breakpoint_id, undone_call_ids, undone_files})
  7. revision+1，广播会话事件；Windows 走现有 501 屏障
```

- 客户端：Dart `ConversationApi` 加 `undoConversation(cid, breakpointId, revision)`；桌面端在出错任务处提供"撤销这次修改"入口，展示断点时间/任务摘要/将回滚文件列表。
- 多文件不是原子事务（沿用 checkpoint 文档约束），逐个原子写；中途失败时 safety 快照可恢复。

### 4.4 回退能力的边界（必须显式告知）

- **可撤销**：被断点覆盖的工作区文本文件、会话展示层状态、未 settle 的轮次。
- **不可撤销**：已发出的网络调用、已执行的命令/SSH 副作用、外部系统状态、模型已经生成的文本（仅在展示层作废）。这与现有 checkpoint 文档一致。
- **引擎差异**：Harness 会话内部历史不可裁剪，`continuation=history_only`；撤销后"续接"只能带展示层已作废之后的内容，需 UI 诚实说明。legacy（Custom）若续接可用，可在撤销后重建上下文，但同样不重跑工具。

## 5. 与现有机制的衔接

| 衔接点 | 处理 |
|---|---|
| `settle_after_restart()` | 扩展：为缺 `critical-after` 的在途工具补一条 `interrupted` 断点；断点本身幂等，重复重启不重复 |
| `store.KINDS` | 增加 `breakpoint`、`undo`；`_searchable` 对二者返回 None；导出/消息页默认过滤，提供独立 `GET /v1/conversations/{cid}/breakpoints` 视图 |
| `ConversationRecorder` | 新增 `breakpoint(...)` 与 `undo(...)` 写入方法，仍作为唯一写入路径；断点钩子由 agent_loop 调用 recorder，不直接写 store |
| `CheckpointService` | 仅在 critical 断点绑定快照时被调用；`snapshot_ref` 回填到断点 payload；撤销时作为回滚载体 + safety 保底 |
| 会话删除级联 | 断点随 conversation_events 级联删除；其绑定的 Git ref 由 `register_before_delete` 回调清理（幂等） |
| 授权边界 | 断点/撤销均经 broker 审批，不新增授权来源；`files_sha256` 与 workspace binding 只做身份/完整性校验 |

## 8. 待确认事项

- `BREAKPOINT_TIMER_SECONDS` 默认值与各 kind 保留数需产品确认。
- Harness 引擎是否暴露"每步"事件；若不暴露，step 断点只能覆盖 legacy（Custom）。
- "任务摘要 goal"由模型声明还是本地推断：模型声明需在工具契约加可选字段，涉及 prompt 变更，建议一期先做 user prompt 摘要。
- 撤销后是否自动发起新的续接（resume），还是只回滚文件与展示层：建议一期只回滚，续接由用户显式操作。
