## Semantics implemented

| Mode | `deny` | `allow` | `confirm` |
| --- | --- | --- | --- |
| `ask` (default) | deny | approve | ask |
| `auto` | deny | approve | approve only the bounded class, otherwise ask |
| `full` | deny | approve | approve authorization-only plans; escalation, `hook:*`, other scopes ask |

- **Scope**: `{workspace_id, target_id}` from the injectable trusted resolver. Mode changes and
  grants are bound to the scope captured at the time of the change; later drift makes `effective`
  false and fails validation until the mode is set again.
- **Revision**: default `0`; every accepted change increments once; `expected_revision` mismatch
  is `409` and does not mutate. `PUT` also requires the current `service_instance_id` (`409`
  otherwise), so a stale UI tab cannot move authority.
- **Default and restart**: a new session is `ask` revision `0`. `close(sid)` drops state and
  grants; a restarted session starts again at `ask`, and decisions from the previous lifetime
  never validate.
- **Engine honesty**: Custom/`legacy` advertises `['ask','auto','full']`; Harness advertises
  `[]`, `effective: false`, mutation `501`. No mode is silently mapped up or down.
- **No grant by reading**: `snapshot()` is pure; repeated `GET`s return byte-identical payloads
  and increment nothing (tested).

### The bounded `auto` class (exact)

All of: `operation == "filesystem.write"`, `rule == "workspace_write"`, `risk == "medium"`,
`scopes == ("authorization",)`, `content_bound_review == True`, `scope_authorized`,
`current_binding`, current `mode_revision`, live scope equal to the bound scope. Anything else —
terminal commands, delegation, hooks, escalation, low/high risk, missing content binding, unknown
rule — asks with a specific reason. The reviewer is deterministic and offline; it never calls a
model, and an unrecognised decision string asks rather than approving.

### Dispatch barrier

`validate(result, input)` re-checks live session, service identity, current revision, current
scope, scope authorization, current binding and fingerprint equality, then **consumes** the
grant: one approval authorizes one dispatch. Replay, cross-session reuse, use after a mode change,
after `close()` and after scope drift all fail (each covered by a test). A turn already running
keeps decisions it already validated; the next dispatch uses the new mode. This is what makes
“revoke/downgrade during a running turn” and “reconnect/history cannot authorize” true at the
service level.

## Pending integration (owner: 06)

Nothing here is enforced until the dispatcher calls this service. Exact recipe:

1. Build one instance in the shared composition:
   ```python
   service = AccessModeService(dependencies, resolve_scope=resolve_live_scope)
   AgentBasics(registrars=(..., lambda app, deps: register(app, deps, service=service)))
   ```
   `resolve_live_scope(sid, controller) -> {'workspace_id': …, 'target_id': …} | None` must use the
   session's current authorized workspace and resolved execution target, never request fields.
2. In `runtime/agent_loop.py` (both adapters) after policy/hooks produce the decision and the
   exact `ActionApprovalPlan` exists:
   ```python
   result = service.review(ReviewInput(
       session_id=controller.id, service_instance_id=service_instance_id,
       mode_revision=snapshot['revision'], operation=request.name,
       fingerprint=plan.fingerprint, decision=decision.action, rule=decision.rule,
       risk=decision.risk, scopes=plan.scopes, scope_authorized=…,
       current_binding=plan.matches(request, decision, policy, execution_target=…),
       content_bound_review=…))
   if result.outcome == 'deny': refuse
   elif result.outcome == 'ask': use the existing broker confirmation
   else: require service.validate(result, input) immediately before dispatch
   ```
   `content_bound_review` is only `True` where the prepared/reviewed diff is actually bound to the
   pending execution (contract clarification: fingerprint alone is insufficient).
3. Call `service.close(sid)` from session close/restart, and flip `access_modes=True` on the
   capabilities route only when routes **and** the barrier are mounted and tested end to end.
4. `apps/desktop` picker (03/06): consume `GET`/`PUT`, render `supported_modes` and `effective`
   honestly, and never fake a switch when `effective` is false.

### Contract clarification request (frozen v1 review)

`scope` is emitted as `null` when no live scope can be proven (then `effective:false`), rather
than a fabricated `{workspace_id,target_id}` pair. Rationale: inventing identifiers would be a
false capability claim. Strict clients must accept `null` here; everything else in the response
matches v1 exactly. If the integrator prefers a non-null shape, the smallest change is an empty
object plus `effective:false`; I did not invent that without agreement.

## Limits

- Mode state is in-memory per live session. It is not durable configuration and must not become
  one: restart must return to `ask`.
- Grant TTL is 900 s by default (configurable) in addition to single use; expiry is tested.
- The audit records are bounded (256) and in memory; persistence/reporting of decisions is a 06/07
  concern and must not store raw arguments or secrets.
- `auto` covers exactly one action class today. Widening it requires a contract revision with
  new tests, not a silent rule addition.
- SSH/remote targets play no part here; scope comes from the live session only.
