# Odessy v0.5.0 planning

Planning decision: October 22, 2026. **Not released; scope is provisional.**

## Desktop application and documentation

Implementation plan: [Flutter desktop UI](../superpowers/plans/2026-10-22-flutter-desktop-ui.md),
using the supplied CC Switch-style device/settings layout and a focused conversation
view. It includes complete feature/configuration coverage, backend API gaps,
role-aware host management, mocked development and platform acceptance gates.

Confirmed direction, October 22: development may start now; delivery targets
v0.5.0. Odessy will have a desktop application, not a browser-based product UI.

- **Desktop:** Flutter + Dart, targeting Windows, macOS and Linux. Platform builds,
  native integrations, signing/packaging and acceptance require separate checks.
- **Documentation:** publish the static documentation on GitHub Pages (`github.io`)
  for v0.5.0. This is documentation hosting, not an application backend. Deployment
  is planned; no site has been published by this decision.
- **Existing services:** retain Python orchestration, model routing and voice, plus
  the TypeScript MCP execution host. The desktop client should initially reuse the
  authenticated session API/events and existing approval boundaries.
- **Native integration proposal:** use Rust for host connectivity, lifecycle or OS
  integration where needed, extending `odessy-link` when appropriate. Use C++ for
  specific native libraries/hardware bindings that require it. A general C++/Rust
  backend rewrite or mandatory extra bridge is not approved by this roadmap;
  choose concrete boundaries before implementation.

Flutter is the selected desktop direction; implementation and cross-platform
qualification are not complete. See [Flutter desktop support](https://docs.flutter.dev/platform-integration/desktop).

## Model detection and selection: no mandatory LFM installation

**Requirement: do not automatically download a complete LFM model or install every
model.** LFM is an optional supported choice, not an onboarding prerequisite.

- Detect an existing Ollama endpoint/service and list its installed models when
  accessible. Also support explicitly configured remote/custom endpoints and
  cloud-only setup; an unreachable service is not proof that no models exist.
- Show detected model names, location/host and availability. Let the user select
  one, enter a supported endpoint/model manually, or choose an optional download.
  Validate compatibility with the selected role; being installed does not prove
  tool-calling or text-only suitability.
- Separate coordinator/capable, Auto fast and consultation participant choices.
  Selecting Auto must not silently pull Gemma or LFM. Explain missing optional
  roles and let the user configure them or continue with a supported single model.
- Before any download, show the selected artifact, source, license, size and disk
  requirements; obtain explicit user consent. Estimate resource needs without
  treating the owner's Jetson 4GB as every user's hardware limit.
- Reuse existing installations/configuration without deleting models, overwriting
  user settings or taking ownership of an independently running service. Preserve
  credential references; do not expose secrets in diagnostics or ordinary responses.
- Distinguish engine installation from optional LLM, Whisper, Kokoro and wake
  assets. A cloud-only engine setup must not require local inference weights.
  Optional voice components can remain unavailable until separately configured.
- Validate the chosen path with bounded checks, actionable failures, cancellation,
  recovery and offline/unreachable states. Test that selecting an installed model
  or cloud-only mode causes **no LFM download**.

These requirements change the future wizard/UI behavior. They do not describe
the current prototype as complete or silently change runtime defaults.

## Go-based multi-host monitoring

Introduce Go for **live health aggregation and device inventory**, a distinct
service rather than another agent runtime, execution host or pairing protocol.
The following boundaries are proposed implementation constraints, not shipped APIs:

- Consume authorized host identity and telemetry through existing trusted transport
  or a narrowly scoped authenticated management API. mDNS is an address hint,
  never enrollment or permission. Do not read private keys or bypass Rust trust.
- Inventory stable enrolled host identity, display name, platform/architecture,
  advertised capabilities, service versions and last-seen time. Unsupported MCU
  families stay declared/unbacked; an inventory entry does not implement operations.
- Aggregate bounded health updates for reachable services: connectivity, heartbeat,
  and CPU/memory/GPU metrics only where a supported collector supplies them. Report
  unsupported, stale, offline and unauthorized separately; never display stale data
  as currently healthy or fabricate GPU metrics across platforms.
- Expose authenticated read-only snapshots and live updates for Flutter/Python.
  Keep authority decisions, pairing grants and tool dispatch in existing services.
- Bound polling, per-host timeouts/concurrency, queues and retained history. A slow
  host must not freeze other hosts. Reconnect without replaying tool work.
- Respect revocation and permission changes. Redact diagnostics and exclude
  credentials, prompt contents and file contents from routine telemetry.
- Start with Windows/Linux and a fake two-host collector; qualify real laptop–
  Jetson monitoring separately. Define the service/collector schema and lifecycle
  before implementation. Persistence and fleet-scale infrastructure are separate
  decisions; no new database/server stack is required by this roadmap.

Acceptance: two authorized hosts update independently; disconnect/reconnect,
stale data, revoked access, slow collectors, missing metrics and orderly shutdown
are tested; the UI identifies each host and measurement time accurately.

## Deferred acceptance carried from v0.4.0

- Physical playback echo/pre-cue admission on the intended deployed audio setup;
  existing software isolation tests and WAV tests do not prove those physical checks.
- The user-deferred one-hour wake false-activation trial, remaining detection/
  interruption measurements and packaged-device acceptance.
- A small current live-cloud evaluation subset and targeted newer collaboration,
  cloud and external-server checks. These can run on a laptop; October 18 saved
  runs remain historical evidence. No automatic paid-provider run is authorized.
- Cross-platform desktop/installer acceptance and applicable dependency/model
  license obligations for the exact redistributed artifacts.

## Deferred or optional, not promised v0.5.0 features

- **MCU operations:** need actual hardware, a firmware contract and conformance
  measurements. Monitoring inventory is not an ESP32/STM32/RP2040 operation backend.
- **Narrowing the execution-target gate:** optional; keep the stricter gate until
  a concrete authorized read-only cross-host use case justifies narrowing it.
- **Further local-model optimization:** measurement-led; saved benchmarks remain
  the baseline, and variable offload success is not a proven optimization.

## Suggested implementation order

1. Sync the desktop branch with released `develop`, keeping the feature branch.
2. Define/model-test detection and selection; finish onboarding without forced LFM.
3. Finish UI workflows against stable client contracts; implement missing backend APIs.
4. Define the monitoring contract, then build Go collectors/aggregation and wire UI.
5. Train/qualify the custom wake model; finish packaging/docs and deployment checks.

No release date, completed implementation or completed hardware qualification is
implied. Retain the Tk installer prototype until its replacement is accepted.
