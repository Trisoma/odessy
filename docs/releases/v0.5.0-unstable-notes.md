# Odessy v0.5.0-unstable: developer preview (pre-release)

Odessy is a local-first AI agent runtime. A model proposes actions; Odessy's Python
policy layer validates them, asks you to confirm risky ones, and runs tools through
an MCP tool server. This is an **unstable prototype for developers**. Expect bugs,
breaking changes and rough edges. Much of the code was written with AI assistance
and is still being reviewed and hardened.

**What works (tested by maintainers on Windows 11 x64, from source)**

- CLI and desktop (Flutter) chat with an existing Ollama model or a cloud API
  (DeepSeek, Claude, OpenAI-compatible).
- Policy-controlled tools (files, search, git, terminal) with approve/reject,
  Stop, and an audit log.
- `python -m odessy doctor` setup diagnostics.

**Support status**

| Platform | Status |
|---|---|
| Windows 11 x64, from source | Preview (the only path we tested end to end) |
| Linux x86_64, from source | Experimental (CI tests only) |
| Jetson Orin Nano 4GB | Experimental: headless, cloud model recommended. Local model plus desktop UI hits GPU out-of-memory. |
| macOS | Untested / unsupported |

**Install:** from source. See the [README quick start](../../README.md#from-source-quick-start). There is no installer in this
release. An attached desktop archive is a UI client only: it connects to
`python -m odessy serve` started from source. It is **unsigned**, so Windows
SmartScreen will warn you. Verify it with `SHA256SUMS.txt`.

## Known limitations

- **Not a sandbox.** Command isolation depends on the host: bwrap on Linux, a *partial* ACL
  boundary on Windows, and largely unavailable on Jetson. Without Node.js,
  `terminal.run` is unconfined. Run Odessy only in a workspace you can afford to lose.
- **Network modes are for trusted networks only.** The LAN execution-host prototype is
  unencrypted HTTP, and `ODESSY_MCP_HOST=0.0.0.0` exposes an unauthenticated
  executor. Use an SSH tunnel or the mTLS `odessy-link` pairing instead.
- **Cloud backends** send your request and redacted tool output to the provider.
- **Voice is optional and needs extra downloads.** You fetch Whisper.cpp, Kokoro and the
  openWakeWord "Hey Jarvis" weights yourself. Those weights are
  **CC-BY-NC-SA (noncommercial)**, and the default phonemizer is GPL.
  Physical-audio acceptance is incomplete.
- **No minimum or recommended hardware has been established.** Local small models are slow
  (tens of seconds per turn on the Jetson 4GB) and unreliable at multi-step tasks.
- **The desktop first run is not guided.** Configure a model in Settings. Pairing, devices
  and monitoring are early previews.
- **Known security advisories (2026-10-31):** `npm audit --omit=dev` reports
  9 affected production packages, all still present in the release lockfile:

  | Severity | Packages |
  |---|---|
  | Critical | `proxy-addr` |
  | High | `@modelcontextprotocol/sdk`, `zod`, `body-parser`, `fast-uri` |
  | Moderate | `hono`, `ip-address`, `qs`, `@hono/node-server` |

  `npm audit fix` (without `--force`) cleared eight findings in a trial, but
  `npm run typecheck` failed before compilation with Windows `EPERM` during
  Node path resolution. The dependency changes were reverted; the fixes
  were not validated, and the remaining tests were not run. Zod is on a runtime
  tool-input validation path and must be treated as potentially reachable. Its
  proposed major-version upgrade requires manual compatibility and security review.
- Version strings read `0.5.0.dev0` (Python) and `0.5.0+1` (desktop). Both are this release.
- Best local Python test run: 2836 passed, 1 environmental flake (`test_component_recovery`, Windows temp-dir lock; passes in isolation). CI on Python 3.12, Windows and Ubuntu is the canonical gate and will re-verify once the repository is public.
- **Known:** `apps/desktop/test/setup_usability_test.dart` fails on Linux (POSIX `fcntl` locks are per-process, not per-handle). The instance guard still blocks a second *process*; only the test's assumption is Windows-specific. Fix planned for `v0.5.0-unstable.1`. `desktop-preview.yml` runs `flutter test` on `ubuntu-latest`, so that job is expected to be red until the fix lands.

## Known review findings (not fixed in this release)

Two findings from the v0.5.0 review remain open. They are recorded here rather than
fixed, because neither was scheduled into this preview. Neither is claimed fixed,
harmless, or covered by a regression test beyond what is stated.

**1. `2>nul` is treated as a null device on every host.** Verified against the current
source: `terminal.run` with `command="ls 2>nul"` is classified `allow` /
`command_read_only`. On Windows that is correct. On Linux, `nul` is an ordinary
filename, so the command creates a file named `nul` in the working directory while
being reported as read-only. The redirect target is a relative path, so the write stays
inside the workspace; this is a prompt bypass and a mislabelled classification for a
small in-workspace write, not a path escape. `2>nul.txt` and `> nul` are correctly
classified as writes. A fix needs host-aware null-device handling, and
`tests/test_permission_hardening.py` currently pins the present behaviour, so the
expectation has to change with the code.

**2. The evaluation harness's `project.grep` ignores a single-file root.** Verified:
grepping `src/storage.py` for `TODO` returns 0 matches, while grepping `src` returns 2.
The cause is the file enumerator in `evals/recording_mcp.py`, which is `root.rglob("*")`
and therefore yields nothing when the root is a file. This affects **eval grading only**:
the shipped TypeScript tool visits the root before recursing and handles a file root
correctly, so no user-facing `project.grep` call is affected. An eval case whose
reference behaviour greps a single file would be graded as a failed tool call.
