# Odessy v0.4.0 roadmap

Planning status: October 20, 2026. **Not released.** v0.3.0 has been released
privately and marked as a prerelease. The items below belong to the v0.4.0 cycle;
placement here does not mean they are implemented or guaranteed for that release.

| Work | v0.3.0 baseline | v0.4.0 work and prerequisites |
|---|---|---|
| Wake-up / wake word | Voice is explicitly invoked and turn-based | Design activation and cancellation, then validate on real audio hardware. No always-on or wake-word support is claimed today. |
| Further local-model optimization | Local adapters and configurable budgets exist; saved results remain the measurement baseline | Measure latency, tool selection, memory, and GPU/offload choices on available hardware before choosing changes. No new speedup is established. |
| Multi-stream tooling | Sequential tool continuation exists | **Merged into `develop` on October 20 via PR #15 (`80ee9b3`), unreleased.** Native cloud and local batches, opt-in overlap for selected built-in reads, ordered results, exclusive barriers, and graceful stop. See [tool concurrency](../reference/tool-concurrency.mdx). Real Jetson validation remains pending. |
| Host pairing | Explicit `ExecutionTarget` authorization exists; authenticated pairing does not | Wait for a concrete remote-host trust scenario and adversary model. Split deployment already supports a configured remote MCP URL; that alone is not pairing. |
| Device operation surface: ESP32 / STM32 / RP2040 | Device families are declared and unbacked; no operation API or hardware backend exists | Wait for a real device, firmware contract, and conformance measurements before defining operations. |
| Voice-based escalation approval | Approval seam is wired end to end; voice mode still uses a console prompt | Decide the composition and explicit spoken approval interaction before implementing it. The model must never approve itself. |
| *Windows signal-kill `exit_code` semantics* | Executor-terminated commands report no exit code (`None` / `null`) | **Decided 2026-10-19, no replacement needed.** Raw process measurements can yield `1` for both termination and failure. Those are not bridge timeout results: the bridge returns `None`, with `timed_out` and `status` carrying the distinction. See `LIMITATION.md`. Separately, `powershell -Command` reports its own status, so a child exit code of 7 arrives as `1`; this remains unchanged. |
| Narrowing the execution-target gate | The gate covers all tool calls, stricter than the process-execution invariant requires | Establish a legitimate read-only cross-host use case before narrowing it; preserve explicit authorization for execution. |
| *Blank audio handling* | `[BLANK_AUDIO]` can reach the model and cause an unnecessary tool proposal | **Implemented in v0.4.0 development, unreleased.** Empty output, known non-speech markers, and punctuation-only transcripts return `blank` before inference; unknown bracketed text remains speech. Actual Whisper `empty` results also retry. `ODESSY_VOICE_BLANK_RETRIES` defaults to 2; 0 disables retries. Integration tests exercise fresh recordings and exactly one agent request after blank/empty attempts followed by speech. **Real-device validation remains necessary.** |

## Extra feature: automatic model selection

Implemented on `feat/auto-model-selection`, unreleased and opt-in:
`--model-backend auto` uses text-only Gemma for narrow greetings and text
transformations, and a configured local capable model for uncertain/tool requests.
Cloud fallback requires explicit enablement and never follows tool dispatch.
Diagnostics retain routing decisions and cumulative generation costs. Jetson
latency and memory qualification remain pending; see
[automatic model selection](../reference/model-selection.mdx).

## Package organization

PR #14 (`f809cee`) merged the package-layout refactor on October 20. Runtime,
model, tool, authority, and configuration modules now live in separate subpackages.
Compatibility imports retain old module identities; regression tests check imports
and repository resource paths. This is unreleased v0.4.0 maintenance work.

## Extra feature: fewer, clearer confirmations

**In development, unreleased.** More read-only commands run unasked (file readers
limited to the workspace, read-only git, program lookup, `--version`). Installers are
rated high risk. The terminal prompt now has two tiers: high risk needs a typed `yes`,
and other commands and third-party tools can be allowed for the rest of the run with
`a` (in memory only). `filesystem.write` shows a diff. See `policy/README.md`.

## Extra feature: third-party MCP servers

**Merged into `develop` on October 19, 2026 via PR #11 (`0f0e191`), unreleased.**
This extends the original v0.4.0 roadmap with opt-in tools from HTTP and stdio MCP
servers listed in `~/.config/odessy/servers.toml` or `ODESSY_SERVERS_FILE`.
Without a servers file, the tool surface is unchanged.

Tools are discovered once at startup and namespaced as `<server>.<tool>`.
Admission checks constrain names and input schemas; each call is validated
against the server's JSON Schema before execution and subject to policy,
confirmation, and explicit execution-target authorization. Configuration controls
trust and per-tool overrides; declared `workspace_paths` are checked even with
an allow override. Limits are 16 external tools for local models and 64 for cloud.

Listing a stdio server launches its program, including during startup discovery.
HTTP calls send arguments to the configured endpoint. Odessy's command sandbox
does not automatically confine third-party server programs or their side effects.
Server descriptions, schemas, annotations, and results remain third-party input.

Follow-ups, implemented in development after PR #11 (unreleased): direct
`jsonschema` dependency declaration; refusal of server and tool names that do not
survive the cloud adapters' `.`/`__` encoding; one kept session per stdio server;
`doctor` checks; and an audit log of third-party calls recording argument hashes,
not values. Evaluation runs do not discover user-configured external servers. See [configuration and decision rules](../reference/external-servers.mdx).

Other unfinished proposals in standalone planning files also move to the v0.4.0
cycle, subject to their stated prerequisites. They are not v0.3.0 release blockers.
Historical benchmark results and earlier release records retain their original versions.
