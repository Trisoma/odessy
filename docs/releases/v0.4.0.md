# Odessy v0.4.0 roadmap

Planning status: October 19, 2026. **Not released.** v0.3.0 has been released
privately and marked as a prerelease. The items below belong to the v0.4.0 cycle;
placement here does not mean they are implemented or guaranteed for that release.

| Work | v0.3.0 baseline | v0.4.0 work and prerequisites |
|---|---|---|
| Wake-up / wake word | Voice is explicitly invoked and turn-based | Design activation and cancellation, then validate on real audio hardware. No always-on or wake-word support is claimed today. |
| Further local-model optimization | Local adapters and configurable budgets exist; saved results remain the measurement baseline | Measure latency, tool selection, memory, and GPU/offload choices on available hardware before choosing changes. No new speedup is established. |
| Multi-stream tooling | Sequential tool continuation exists | Define what streams may overlap, their cancellation and ordering, and how authorization applies before implementing concurrency. This is separate from existing multi-step calls. |
| Host pairing | Explicit `ExecutionTarget` authorization exists; authenticated pairing does not | Wait for a concrete remote-host trust scenario and adversary model. Split deployment already supports a configured remote MCP URL; that alone is not pairing. |
| Device operation surface: ESP32 / STM32 / RP2040 | Device families are declared and unbacked; no operation API or hardware backend exists | Wait for a real device, firmware contract, and conformance measurements before defining operations. |
| Voice-based escalation approval | Approval seam is wired end to end; voice mode still uses a console prompt | Decide the composition and explicit spoken approval interaction before implementing it. The model must never approve itself. |
| Windows signal-kill `exit_code` semantics | Executor-terminated commands report no exit code (`None` / `null`) | Review native Windows termination semantics and decide whether any distinction is needed. The current answer remains valid; no replacement is decided. |
| Narrowing the execution-target gate | The gate covers all tool calls, stricter than the process-execution invariant requires | Establish a legitimate read-only cross-host use case before narrowing it; preserve explicit authorization for execution. |
| Blank audio handling | `[BLANK_AUDIO]` can reach the model and cause an unnecessary tool proposal | Detect blank/unusable transcripts before inference, offer a retry, and verify that no model or tool call occurs. Real-device validation remains necessary. |

Other unfinished proposals in standalone planning files also move to the v0.4.0
cycle, subject to their stated prerequisites. They are not v0.3.0 release blockers.
Historical benchmark results and earlier release records retain their original versions.
