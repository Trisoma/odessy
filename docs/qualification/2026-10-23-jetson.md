## Real local model checks

Q8 only; saved `odessy-lfm-q8:jetson` profile declares 15 GPU layers, batch 64,
context 1024. No saved profile or service settings were changed.

Auto initially selected Gemma for a greeting, then escalated with `fast_failed`.
The Q8 fallback and a time-tool request failed to load with CUDA out-of-memory.
Direct API retries reproduced this outside Odessy. Two fixed 15-layer requests
failed allocating 1,101,179,904 bytes; 12 layers failed at 893,856,256 bytes.
CPU-only generated 128 thinking tokens but no final answer at that limit.
Temporary 1-layer and 6-layer requests each completed with “Hello!” at 256-token
limits. These are functional observations under changing memory state, not a
controlled performance benchmark. No service MemoryMax/MemoryHigh cap was set.

GPU utilization is distinct from model placement. With explicit 15 layers, Ollama
reported it could not fit the user-selected value; automatic placement was not
established for those failing requests. Memory pressure/fragmentation remains a
possible explanation, not a proven root cause.

After the smaller-offload/CPU requests, a final unchanged 15-layer direct request
also completed with “Hello!” in 15.11 s. The changed outcome under changed memory
state is recorded alongside the earlier failures; it does not establish reliable
15-layer residency or erase the failed Auto runs.

Subsequent Odessy Auto retries completed both greeting and time requests. Greeting
first selected Gemma, then visibly fell back to Q8 with `fast_failed`; time selected
Q8 with `uncertain_or_tool_request`. The exact Gemma adapter reproduced an empty
answer. Direct non-streaming Ollama with the same text-only system prompt and
temperature 0 also returned empty content, `done_reason=stop`, `eval_count=1`.
A simpler direct greeting prompt returned “Hello there!”. The cause is not
established; this is not evidence that the stream accumulator lost an answer.

## Full Q8 voice trial

The first bounded real-Q8 session ended at its test deadline after the user began
speaking late; no completed answer was recorded. A longer repeat reached speech
transcription and model generation. Ollama reported 20% CPU / 80% GPU placement;
a tegrastats sample showed 2,924/3,602 MB RAM and 647/1,801 MB swap in use.
The turn then failed after its one repair retry: neither tool call nor final
content was returned. Ollama logged a complete 512-token generation allowance
at about 14.23 tokens/s. Thinking-budget exhaustion is consistent with this result
but needs a larger-budget controlled trial. Full Q8 voice acceptance remains
**failed/incomplete**, despite successful model loading and fake-model audio.

A temporary 2048-context / 1024-generation-budget session later produced a time
answer after spoken input. A concurrent typed request was correctly rejected as
busy. Switching `/text` during generation preserved the active turn but purposely
disabled speech output; the user's lack of audible output in that trial is not
evidence of a TTS failure. A further output-enabled typed-input trial follows.

The later typed time request completed successfully within the voice session at
2048/1024. Typed turns intentionally display text rather than invoke speech output;
this verifies typed admission/result delivery, not a new audible TTS pass.

A final session without the short coordination timeout completed a real spoken
turn at 15 GPU layers / context 2048 / generation budget 1024. It replied
“What specific task or information do you need help with today?” and launched
`aplay` on the JBL output. The user confirmed clear playback and that the question
was how the assistant was doing. This establishes an end-to-end Q8 voice smoke
pass at those temporary settings, not stable residency or latency qualification.
Memory observation near playback: 2.9 GiB RAM used, 814 MiB swap used. The session
was closed explicitly through `/exit`; saved configuration was unchanged.
